# Process 1A — Xbox 360 source-0 gate at `0x7FC86544`

**Дата:** 2026-10-24. **Режим:** report-only; никаких изменений кода, runtime/guest state и renderer.  
**Исходная идентичность (предоставлена пользователем, не перепроверена по бинарникам):**
- Retail Xbox 360 `default.xex` SHA-256: `8c86a34f369f9d064126342daccb2cfe4646cfe735df6a032812a40a9c0a2c58`.
- Live-memory ELF SHA-256: `2ffe352bda115285e58661cb5fc5ebe1a0c845d1e7a9ae07bee89e514636c00c`.
- Архитектура retail кода: PowerPC big-endian.

## 1. Фактическое покрытие XREF-поиска и ограничения

**Достоверно проанализирован только полный предоставленный PPC-блок `0x823B37B8..0x823B3848` (включая последнюю инструкцию по `0x823B3848`).** В нём есть **один явный reader** `0x7FC86544`, **ни одного writer** в этот адрес. Это *не* исчерпывающий XREF по всему retail XEX.

Проверен доступный загруженный `SHIFT_objdump_full.txt`: это disassembly **Windows PE32/i386 `SHIFT.exe`**, а не Xbox 360 PPC XEX / live-memory-derived ELF; поиск точных `7fc86544`, `7fc8...6544` и `0x823b3830` в нём не дал совпадений. **Нулевая выдача из иного исполняемого файла не даёт отрицательных XREF-доказательств для Xbox XEX.** Исходный PPC ELF/полный PPC image, пригодный для сканирования всех PPC инструкций и таблиц по всему адресному пространству, в рамках этого задания не предоставлен. В частности, не проверены writer'ы через регистр с динамически вычисляемым адресом, через другие MMIO/host пути или из другого кода.

Строгое резюме по области покрытия:

| Категория | Адреса | Статус |
|---|---|---|
| Прямое чтение именно `0x7FC86544` | `0x823B3830` — `lwz r11,0x6544(r11)` после `lis r11,0x7FC8` | Подтверждено инструкциями |
| Проверка его bit 0 | `0x823B3834` — `clrlwi. r11,r11,31` | Подтверждено |
| Потребитель результата ветки | `0x823B3838` → `0x823B383C..0x823B3840` | Подтверждено |
| Записи `0x7FC86544` | **Не найдены в данном PPC-блоке** | Не означает отсутствие writer'ов в XEX |
| Все возможные indirect/dynamic references во всём XEX | Не установлены | Недостаточный охват |

## 2. ABI handler и source-0 control flow (статические факты)

На входе `0x823B37B8`: `r3` — **селектор события**, сравниваемый с `1` и `0` (содержательное название/тип селектора требует caller); `r4` — указатель на объект, сохраняемый в `r31` на `0x823B37C4`. Пролог использует сохранение register state через `0x826D98CC`, локальный стек `0x70` байт. Прямого контракта возвращаемого значения в этом блоке нет.

- `0x823B37C8`: `cmplwi cr6,r3,1`; `0x823B37CC`: `bf 26` **если `r3 != 1`**, переход к `0x823B3824`.
- `0x823B3824`: `cmplwi cr6,r3,0`; `0x823B3828`: `bf 26` **если `r3 != 0`**, переход прямо к общему эпилогу `0x823B3844`.
- **Только для `r3 == 0`**:
  - `0x823B382C`: `lis r11,0x7FC8` → `r11=0x7FC80000`.
  - `0x823B3830`: `lwz r11,0x6544(r11)` → чтение 32-битного значения по **`0x7FC86544`**.
  - `0x823B3834`: `clrlwi. r11,r11,31` → `r11 = value & 0x00000001`, CR0.EQ устанавливается при нуле. Это извлечение **bit 0**, не atomic read-modify-write.
  - `0x823B3838`: `bt 2,0x823B3844` → при **bit 0 == 0** пропуск consumer.
  - `0x823B383C`: `mr r3,r31` → `r3=O`; `0x823B3840`: `bl 0x823A4640` — при **bit 0 == 1** прямой вызов consumer с объектом.
- Эпилог `0x823B3844..0x823B3848`; в этом пути handler **не** записывает `0x7FC86544`, не модифицирует deferred read/write indices и не обращается к callback slot `O+0x409C` напрямую.

Таким образом, **для прямого вызова `0x823A4640` в рамках именно этого обработчика необходимы `r3==0` и `(load32(0x7FC86544)&1)!=0`**. Из этого не следует ни происхождение бита, ни статус/семантика аппаратного регистра, ни наличие/отсутствие элементов очереди.

## 3. Другой путь handler: selector 1 (не смешивать с MMIO gate)

При `r3==1` (`0x823B37D0..0x823B3820`) код:
1. Загружает указатель `P=load32(O+0x2A94)`.
2. Читает `fn=load32(P+0x10)`. При `fn!=0` передаёт `r3=load32(P+0x14)` и делает `mtctr fn; bctrl` (`0x823B37E0..0x823B37E8`).
3. Адресует `O+0x2A98` и вызывает `0x83063D4C`, затем читает byte `*(r13+0x10C)`, вычисляет `1 << shift` инструкцией `slw` и очищает этот бит из `load32(P+0)` через `andc`; `clrlwi ...,26` дополнительно сохраняет только младшие 6 бит; `stw` обновляет `P+0` (`0x823B3808..0x823B3818`). Вызывает `0x83063D1C` и уходит в эпилог.

Это **запись по адресу `P+0`**, где `P` получен из `O+0x2A94`, а не установленная статически запись `0x7FC86544`. Равенство `P==0x7FC86544` никакой инструкцией данного блока не доказано. Предположение о lock/unlock на основании парных helper-вызовов допустимо как гипотеза, но тип/синхронизация не выводятся без callee inspection. Ветка selector 1 **не** вызывает `0x823A4640`.

## 4. Отдельно переданное runtime-наблюдение

В ограниченном Linux run срабатывал вход `0x823B37B8`, а затем был фактически вызван `0x823A4640` (consumer). Следовательно, **для хотя бы этих фактических вызовов через показанный callsite** была выбрана ветка `r3==0` и проверка **bit 0 дала ненулевой результат**; иначе execution данного callsite не достигается. Это не устанавливает bit 0 для других моментов, не указывает writer, не подтверждает вызов producer `0x823A4758`, и не доказывает, что queued work имелся.

Ранее отдельно переданные sample read/write indices deferred ring `O+0x413C/+0x4140=0/0` совместимы с тем, что consumer допускается в работу **даже при пустой очереди**: MMIO gate допускает вход, а очередь затем может оказаться пустой. **В данном наблюдавшем path бит 0 сам по себе не объясняет отсутствие записей в deferred ring**. В других моментах/состояниях нулевой бит может пропускать consumer, но причинность отсутствия enqueue из этого не следует.

Важно не отождествлять `0x7FC86544` с **другим** MMIO адресом `0x7FC86110`, используемым в ранее представленном PPC producer/consumer коде: адреса различны, и взаимозависимость не установлена.

## 5. Интерпретации и неизвестное

**Доказано:** `0x7FC86544` — явный memory-mapped-like адрес чтения в source-0 ветке; значение `&1` непосредственно контролирует **переход к вызову `0x823A4640`**. Handler не ставит и не снимает этот бит.

**Гипотеза:** бит может сигнализировать одно из состояний источника GPU interrupt или готовность/наличие работы. Однако наличие `consumer` call при `0/0` **не позволяет назвать его nonempty/readiness-предикатом deferred queue**, тем более что интерпретация MMIO register и writer неизвестны.

**Неизвестно:** все остальные XREF в полном Xbox PPC image; кто записывает бит 0; когда MMIO значение обновляется и кем (guest, host/GPU emulation, hardware); что означает selector `0/1` на уровне внешнего API; изменяются ли данные очереди между наблюдениями; связь gate с frontend progress или black readback. Нулевых direct-XREF-совпадений в Windows/i386 `SHIFT.exe` недостаточно для отрицательных утверждений о retail Xbox XEX.

## 6. Один следующий проверяемый путь

**Пассивный guest-MMIO write tracepoint на 32-битном адресе `0x7FC86544`**: регистрировать write PC/LR (либо host handler origin, если MMIO обновляется вне guest), thread/source, прежнее/новое значение и bit 0. Сопоставлять таймстемпы с `0x823B3830` и входом в `0x823A4640`, не подменяя gate, не меняя данные и не форсируя очередь. Если гостевых записей нет, это само по себе не исключает host-side обновление MMIO; для выяснения этого нужен отдельный trace соответствующего handler.
