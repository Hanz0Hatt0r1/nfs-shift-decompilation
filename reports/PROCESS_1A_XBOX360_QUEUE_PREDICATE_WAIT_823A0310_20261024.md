# Process 1A — Xbox 360 retail queue-predicate wait `0x823A0310`

**Дата:** 2026-10-24  
**Область:** одна PPC32 big-endian функция `[0x823A0310, 0x823A03E8)` — `0xD8` байт, **54 инструкции**; следующая function entry `0x823A03E8`.  
**Режим:** report-only; без изменений кода, guest wait, runtime gates, retail semantics и без публикации бинарников/частных источников.

## 2. ABI и поля

**[S] PPC ABI.** Входное `r3 = context*`, причём `lwz r29,0(r3)` на `0x823A031C` извлекает `object*` из первого слова контекста; `r31 = context*` сохраняется на `0x823A0320`. Функция возвращает **`r3 = 0` или `r3 = 1`**. Входные `r4`–`r10` как параметры в данном теле не используются. `r29/r30/r31` удерживают контекст, локальное 32-битное значение и объект через вызовы. `mflr r12; bl 0x826D98CC` и завершающий `b 0x826D991C` (`0x823A0310..0314`, `0x03E4`) — внешняя пара пролога/эпилога; её внутреннее устройство данным блоком не раскрывается.

| Адрес/поле | Чтение | Запись | Доказанная операция |
| --- | --- | --- | --- |
| `context+0x00` | `0x031C` | нет | 32-битный указатель на объект в `r29` |
| `context+0x08` | `0x036C` | `0x0388` условно | сохранённое ранее значение `*(*(object+0x2A90))`; обновляется при несовпадении |
| `context+0x0C` | `0x03AC` | `0x0384`, `0x03A8`, `0x03D4` условно | сохранённое значение `r30` из thread/PCR-derived цепочки; база для беззнаковой разности |
| `object+0x2ABD` | `0x0358` `lbz` | нет | флаг; проверяется маска `0x02` |
| `object+0x2A90` | `0x0364` `lwz` | нет | указатель на 32-битное слово; последующее `lwz 0(pointer)` |
| `*(object+0x2A90)+0x00` | `0x0370`; повтор `0x0380` только при mismatch | нет | текущее слово для сравнения с `context+0x08` |
| `object+0x2A88` | `0x0390` | нет | сравнение с возвратом `0x826F0380()` |
| `object+0x2B00` | `0x039C` условно | нет | ненулевое слово включает дополнительный сброс `context+0x0C` |
| `*(r13+0x100)+0x58` | `0x0368`, `0x0374` | нет | `r10 = *(u32*)(r13+0x100)`; `r30 = *(u32*)(r10+0x58)` |

`context+0x04` блок не читает и не пишет; минимально доступный размер контекста — `0x10` байт (при корректном вызывающем коде). Все перечисленные поля — 32-битные, кроме байта `object+0x2ABD`. Указатель `object+0x2A90` разыменовывается **без локальной null-проверки**. Данный блок не изменяет память объекта и не обращается непосредственно к MMIO/GPU-регистрам.

**[S] Пауза перед предикатом.** `0x0328..0x0350`: `li r11,4; mtctr r11`; восемь `mr r31,r31` на каждом проходе и `bdnz 0x0330` — четыре прохода, всего 32 самоприсваивания. Они не обновляют queue-поля; только потребляют инструкции и меняют CTR. `mr r2,r2` на `0x0354` также ничего не меняет.

## 3. Точные условия ветвления и return-пути

**[S] Сначала `object+0x2ABD` (`0x0358..0360`).** `lbz r11,0x2ABD(r29); rlwinm. r11,r11,0,30,30` оставляет **маску `0x02`** и обновляет CR0. `bf 2,0x823A03DC` проверяет **CR0.EQ = false**, а не «bit отсутствует»:

- `(flag & 0x02) != 0` → `CR0.EQ=0` → переход на `0x03DC: li r3,0` → return **0**. Никаких чтений `object+0x2A90` или вызовов `0x826F0380/0x823BA9C8` на этом пути.
- `(flag & 0x02) == 0` → `CR0.EQ=1` → переход **не** выполняется, начинается проверка снимков и порога.

**[S] Изменение наблюдаемого слова (`0x0364..038C`).** `r9 = context[0x08]`, `r8 = *(u32*)object[0x2A90]`, `r30 = *(u32*)(*(u32*)(r13+0x100)+0x58)`. `cmplw cr6,r9,r8; bt 26,0x038C` пропускает обновление при **равенстве**. При неравенстве повторно читается `*object[0x2A90]`; `context[0x0C] = r30`, `context[0x08] = повторно_прочитанное_слово`. Второе чтение по `object+0x2A90` не обязано равняться первому при конкурентном изменении; атомарность пары не доказана.

**[S] Дополнительный сброс базы (`0x038C..03AC`).** Вызов `0x826F0380()` возвращает значение в `r3`. `cmplw cr6,object[0x2A88],r3; bf 26,0x03AC` пропускает проверку `object+0x2B00` при **неравенстве**. При равенстве, `cmpwi cr6,object[0x2B00],0; bt 26,0x03AC` пропускает запись, если слово равно нулю. Только при **одновременных** условиях `object[0x2A88] == return(0x826F0380)` и `object[0x2B00] != 0` выполняется `context[0x0C] = r30` на `0x03A8`. Назначение `0x826F0380` не установлено.

**[S] Порог 5000 (`0x03AC..03C4`).** `sub r11,r30,context[0x0C]` вычисляет 32-битную разность по модулю `2^32`. `cmplwi cr6,r11,5000; bf 24,0x03C4` использует **CR6.LT**: переход к helper происходит, если **не** `delta < 5000`, то есть при `delta >= 5000` **по беззнаковому сравнению**. Если `delta < 5000`, `li r3,1` на `0x03BC` → return **1**. Это порог `5000` единиц поля `r30`; единицы времени/природа поля не доказаны.

**[S] Helper (`0x03C4..03DC`).** При `delta >= 5000`: `r3=object`; `bl 0x823BA9C8`; `cmpwi r3,0; bf 2,0x03DC`:

- `return(0x823BA9C8) != 0` → `CR0.EQ=0` → return **0**, без обновления `context+0x0C` на этом пути.
- `return(0x823BA9C8) == 0` → `context+0x0C = r30` (`0x03D4`), затем `b 0x03BC` → return **1**. Используется **ранее снятый** `r30`, а не новое чтение после helper.

Других достижимых `li r3,0/1` на рассматриваемых путях нет. Оба возвращаемых значения проходят общий эпилог `0x03E0..03E4`.

### Эквивалентная модель управления потоком (не реконструкция исходных типов/имён)

```c
// Только поведение [S], типы условные; PPC32 BE, wraparound unsigned.
u32 predicate_wait(Context *c) {
    Object *o = (Object *)c->object_at_0;
    // фиксированный CTR-цикл: 4 * 8 self-moves

    if ((load_u8(o + 0x2ABD) & 0x02) != 0)
        return 0;

    u32 p = load_u32(o + 0x2A90);    // адрес 32-битного слова
    u32 prev = load_u32(c + 0x08);
    u32 first = load_u32(p);
    u32 thread_data = load_u32(r13 + 0x100);
    u32 current = load_u32(thread_data + 0x58);

    if (prev != first) {
        store_u32(c + 0x0C, current);
        store_u32(c + 0x08, load_u32(p)); // второй load, не first
    }
    u32 a = call_826F0380();
    if (load_u32(o + 0x2A88) == a && load_u32(o + 0x2B00) != 0)
        store_u32(c + 0x0C, current);

    u32 delta = current - load_u32(c + 0x0C);
    if (delta < 5000u)
        return 1;
    if (call_823BA9C8(o) != 0)
        return 0;
    store_u32(c + 0x0C, current);
    return 1;
}
```

Примечание к псевдокоду: в реальном коде `lwz r30,0x58(r10)` стоит до `cmplw cr6` и ветвления `0x0380`; модель сохраняет эквивалентный порядок всех существенных чтений, кроме условных повторных чтений.

## 4. Контракт с caller `0x823A4E48`, вызов `0x823A55B8`

**[R: переданный статический контекст caller, не повторно дизассемблирован в этой задаче]** `0x823A55B8` вызывает `0x823A0310` с `r3` — адресом stack context. После возврата caller проверяет `r3` и при ненулевом значении **может** повторить вызов, дополнительно ограничивая разницу собственных объектных счётчиков. Полного листинга caller после `0x823A55B8` в материале этого задания нет; точные `CR`/branch-offsets, номер счётчика и смысл его границы **здесь не подтверждены**.

**[S + переданный контекст caller]** Callee `r3=0` исключает повтор именно через ветвь caller, требующую `r3 != 0`; это не доказательство завершения всего кадра, всей функции caller или frontend. Callee `r3=1` **разрешает**, но не гарантирует следующую итерацию: решение зависит также от проверки объектных счётчиков и других ветвей caller. Возврат `1` возможен как после `delta < 5000`, так и после `helper == 0`; это **не** самостоятельный признак прохождения GPU работы.

**[S] Флаг в действительности ориентирован так:** при **установленном** `object+0x2ABD & 0x02` данный predicate сразу возвращает `0` и **обходит** пороговый/helper-путь; при **отсутствующем** бите входит в него. Поэтому формулировка «отсутствие bit `0x02` пропускает GPU queue sync wait» неверна, если под «пропускает» понимается skip/bypass. При отсутствии бита возможен `r3=1` и повтор caller-loop, но утверждать бесконечное ожидание или frontend stall нельзя.

**[I] Семантика «GPU queue sync wait».** Название стадии оправдано окружающим queue-контекстом задания, но внутри `0x823A0310` нет GPU-поллинга или ожидания ОС как явно идентифицированной инструкции. Назначение `0x823BA9C8` и `0x826F0380`, единицы поля `r30`, состояние caller при `r3=0`, а также связь с показом frontend остаются неизвестными. Отсутствие per-pixel readback дополнительно запрещает утверждать визуальный прогресс.

## 5. Runtime evidence — отдельно от статического анализа

**[R1, отдельный 60-секундный Linux/GDB запуск]** `0x823B33A0` hit **27** раз; software-queue tail `object+0x2A9C` вырос **3 → 3003**; global `0x831B3820` оставался **0**; наблюдались отдельные выборки predicate byte **`0x04`/`0x14`**; breakpoint’ы останавливали guest. Значения `0x04` и `0x14` сами по себе **не содержат bit `0x02`**, но нельзя переносить их на каждый вход `0x823A0310` без синхронного сэмплирования.

**[R2, другой 45-секундный запуск]** source-0 callback достигал `0x823A4640`; deferred indexes `object+0x413C/+0x4140` были **0/0**; candidate producer `0x823A4758` не имел hits. **Не** совмещать эти значения с R1 как последовательные события.

**[R3, отдельная 30-секундная Linux-проба]** Vulkan plugin hash `e05ea50726caea536e25f0e3f76d052e56740bdc455fb26d0884ecab8e8adfdd`. Per-pixel readback отсутствовал; frontend progress **не** доказан. Эта проба не определяет логику return-путей данного PPC-блока.

Ни один из R1–R3 не содержит полного согласованного trace `caller(0x55B8) -> callee -> caller-branch`; runtime-контракт ими не установлен.

## 6. Следующий read-only tracepoint для точного caller/callee контракта

Один и тот же **run ID**, thread ID, host/guest monotonic timestamp (разделённо), номер итерации caller и contiguous событие вход→выход→ветвь. Собирать без изменения флага, семантики ожидания, GPU путей или подмены результата; при breakpoints отмечать guest pauses.

1. **До `0x823A55B8` (caller):** `PC/LR`, `r3` (адрес stack context), `[r3+0x00]`, `[r3+0x08]`, `[r3+0x0C]`; фактические два счётчика/offsets caller, вычисленную им разность/ограничение, индекс итерации и базовый `object*`. Снять **сырые инструкции и условие ветви** caller после return, прежде чем именовать её «loop».
2. **На входе `0x823A0310` и `0x0358..0360`:** `r3/r29/r31`, `object+0x2ABD` целиком, `&0x02`, CR0.EQ и факт `bf 2`; `object+0x2A90` (сам указатель), `*(object+0x2A90)`, сохранённое `context+0x08`. Нужны pointer validation и snapshots, не только маскированный байт.
3. **После `0x0374` и на `0x038C..03AC`:** `r13`, `*(r13+0x100)`, `r30=*(...+0x58)`, обе отдельные выборки `*object[0x2A90]` (если второе чтение произошло), `context+0x08/+0x0C` до/после, возврат `0x826F0380`, `object+0x2A88`, `object+0x2B00`; CR6.EQ и срабатывание каждого сброса базы.
4. **На `0x03B4/0x03B8`:** точные `u32 r30`, `u32 context+0x0C`, `u32 delta=(r30-base)&0xFFFFFFFF`, CR6.LT и сравнение с `5000`. Если есть call `0x823BA9C8`, записать входной `r3=object` и фактический возвращённый `r3` на `0x03CC`, а также состояние `context+0x0C` на `0x03D4`.
5. **На `0x03DC/0x03E0` и сразу после возврата к caller:** код причины `flag_set / delta_lt_5000 / helper_nonzero / helper_zero`, финальное `r3`, изменения `context+0x08/+0x0C`; конкретный результат caller counter-bound compare, PC следующей ветви и **совершён ли фактический повтор** `0x823A55B8`. Отдельно маркировать exit из локального loop и действительный frame/present/frontend progress — это разные наблюдения.

Приоритет — один цельный trace нескольких соседних итераций **одного запуска** с отдельными причинами возвратов, прежде чем делать выводы о stalled frontend или deferred-queue causal chain.

## 7. Статус

**[S] Установлено:** входной `context*`, `object*` из `context+0`, четыре поля объекта и цепочка thread/PCR-derived чтения, условные обновления двух полей контекста, точная полярность flag `0x02`, беззнаковый порог `5000`, все пути return `0/1`, вызовы `0x826F0380` и `0x823BA9C8`.

**[R] Передано, но не проверено данным блоком:** три раздельные runtime-пробы, caller в `0x823A55B8` и его дополнительный counter bound.

**[I] Остаётся неизвестным:** тип/единицы thread-derived поля, значения helper’ов, точная логика caller после вызова и причинность по отношению к frontend. **Никаких retail semantic patches или gate/wait bypass не предлагается.**
