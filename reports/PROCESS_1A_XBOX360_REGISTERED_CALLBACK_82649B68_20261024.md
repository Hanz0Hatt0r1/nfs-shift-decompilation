# Process 1A — registered retail Xbox 360 callback `0x82649B68`

**Дата:** 2026-10-24  
**Тип:** report-only, PPC big-endian, без изменений retail/runtime/code/renderer/P2.  
**Границы:** `[0x82649B68, 0x82649C94)` = `0x12C` байт, **75 инструкций**. Следующая entry `0x82649C94`.

## 1. Идентичность и доказательная база

- Xbox 360 retail `default.xex`, переданный SHA-256: `8c86a34f369f9d064126342daccb2cfe4646cfe735df6a032812a40a9c0a2c58`.
- Live-memory-derived ELF, переданный SHA-256: `2ffe352bda115285e58661cb5fc5ebe0a8c845d1e7a9ae07bee89e514636c00c`.
- **[S] Статика, высокая уверенность:** полностью предоставленные байты и мнемоники `0x82649B68..0x82649C90`, непосредственно получаемые из них effective addresses, dataflow, CR6-условия и control flow. Хеши не пересчитывались.
- **[R] Runtime, переданный независимо:** один 45-секундный exact-XEX Linux/GDB запуск с выборочными breakpoints. См. §6; не выводить отрицание достижимости из отсутствия hits.
- **[I] Интерпретация:** предполагаемое назначение state/counters и отношение callback к очереди; не является доказанным смыслом этих адресов.

## 2. ABI и полное направление dataflow

**[S] Входной аргумент в `r3` в теле не читается.** Последовательность `0x9B68..0x9B70` сохраняет LR и создаёт stack frame `0x60` байт, не обращаясь к `r3`. Затем `lis r11,0x8312; addi r3,r11,0x2BB0` на `0x9B74/0x9B78` **перезаписывает входной `r3` константным адресом `0x83122BB0`**, после чего `bl 0x821A7BA8` на `0x9B7C` вызывает прямой helper. Переданный producer stack record (если producer передал его в `r3`) **не читается, не разыменовывается и не изменяется явными инструкциями этого callback**. Нельзя делать вывод о скрытых эффектах внешнего `0x821A7BA8` без его тела; прямого указателя на producer record ему здесь не передаётся.

**[S] Возврат helper.** Результат `0x821A7BA8` в `r3` используется в `0x9B94` и сохраняется в глобальной структуре; далее в рассматриваемом теле `r3` не переписывается. При обычном соблюдении PPC ABI функция возвращается с тем же `r3`, но **назначение результата callback для producer и полноценная прототипная сигнатура не установлены**. В функции два эпилога, `0x9C30..0x9C3C` и `0x9C84..0x9C90`, оба восстанавливают LR/SP. Нет косвенного вызова; единственный `bl` — к `0x821A7BA8`.

**[S] Глобальные адреса:**

- `0x9B80/0x9B84`: `lis r11,0x8312; addi r11,r11,0x2B90` → **`base = 0x83122B90`**.
- `0x9C08/0x9C0C` и `0x9C5C/0x9C60`: `lis r8,0x8309` → `0x83090000`; `lwz -12048(r8)` и `stw -12048(r8)` дают **`0x8308D0F0`**, потому что `-12048 = -0x2F10`. Это обязательное исправление опечатки `0x8309D0F0` из исходной формулировки; фактический адрес — **`0x8308D0F0`**.

| Глобальное поле | Смещение от `0x83122B90` | Доступ (32-bit `lwz/stw`) | Доказанный эффект |
| --- | --- | --- | --- |
| `0x83122B8C` | `-0x04` | read/write `0x9BF4..0x9BFC`, `0x9C7C..0x9C80` | отдельный счётчик: инкремент на ветви predicate=1/state=0; сброс на predicate=0/state=0 |
| `0x83122B90` | `+0x00` | read/write `0x9C48..0x9C50`, `0x9C28..0x9C2C` | обратный счётчик: инкремент predicate=0/state=0; сброс predicate=1/state=0 |
| `0x83122B94` | `+0x04` | read `0x9B88`, write `0x9BA8` | прежняя разность, заменяется вновь вычисленной разностью |
| `0x83122B98` | `+0x08` | write `0x9BA0` | копия прежнего значения из `base+0x04` |
| `0x83122B9C` | `+0x0C` | read `0x9B8C`, write `0x9B98` | прежнее значение helper, заменяется свежим `r3` |
| `0x83122BA0` | `+0x10` | write `0x9C20` или `0x9C74` | значение `1` либо `2`, только после соответствующей проверки счётчика/global |
| `0x83122BA4` | `+0x14` | read `0x9BE4` | общий gate для обеих ветвей; когда ненулевой, они обходят обновление счётчиков |
| `0x83122BA8` | `+0x18` | write `0x9BDC` | текущий булев результат порогового теста (0/1) |

| `0x83122BB0` | отдельный прямой аргумент `0x821A7BA8` | как константный адрес в `r3` | содержимое указателя в этом блоке **не** читается |
| `0x8308D0F0` | другой global | read `0x9C0C/0x9C60`; write `0x9C24/0x9C78` | условно присваивается 0 или 1, с разными gate-проверками |

Все приведённые global accesses — 32-битные `lwz/stw`. Внутри callback нет объектных offset-accesses по входному producer `r3`. Имена/типы полей в таблице — описания операций, а не реконструированные символы.

**[S] Вычисление нового значения `r9`:**

1. `r10 = load32(base+0x04)` — старое последнее delta.
2. `r9 = load32(base+0x0C)` — прошлое значение helper.
3. `r8 = load32(base+0x1C)` — selector (снимок).
4. `r3 = call 0x821A7BA8(0x83122BB0)`.
5. `0x9B94: sub 9,3,9`, машинный PPC `subf RT=9,RA=9,RB=3` → **`r9 = r3 - old_sample`**, не `old_sample - r3`. При чтении alias-мнемоники приоритет у расположения полей.
6. `0x9B98: base[+0x0C] = r3`; `0x9BA0: base[+0x08] = old_delta`; `0x9BA4: r10 = r9 + old_delta`; `0x9BA8: base[+0x04] = low32(r9)`.

То есть порог проверяется для **суммы нового delta и предыдущего delta**, а не отдельно для текущей разности. Архитектурная GPR-арифметика не предполагает установленной физической размерности данных. `stw` сохраняет нижние 32 бита; `cmplwi` далее сравнивает unsigned word, также значимы нижние 32 бита суммы.

## 3. Пороговые ветви `0x82649B9C..0x82649BE0`

`0x9B9C: cmpwi cr6,r8,0`; `0x9BAC: bt 26,0x9BC0` выбирает ветку при **selector == 0**. `bf 25` — ветвление, когда условие CR6.GT **ложно**; `bt 24` — ветвление, когда CR6.LT **истинно**. `r10` до установки флага содержит `new_delta + old_delta` (сравнение `cmplwi`, unsigned word).

| `base+0x1C` | Инструкции | Условие `base+0x18=1` | Иначе |
| --- | --- | --- | --- |
| `!=0` | `0x9BB0..0x9BBC`, `0x9BCC..0x9BD8` | **`80 < unsigned32(r10) < 161`**, то есть `81..160` | `0` |
| `==0` | `0x9BC0..0x9BD0` | **`67 < unsigned32(r10) < 134`**, то есть `68..133` | `0` |

**[S]** При нижнем пределе используется `cmplwi ... 80/67; bf 25` (отбрасывает `<=`), при верхнем — `cmplwi ... 161/134; bt 24` (принимает строгое `<`). После `li r10,1` или `li r10,0` выполняется `clrlwi r10,r10,24` и **`stw r10,0x18(r11)`** на `0x9BDC`. Последующее `cmpwi cr6,r10,0` в `0x9BE0` — ветвление по **вычисленному predicate**, а не по selector.

## 4. Два различных пути после `0x82649BE0`

Общее до развилки: `base[+0x18]` **всегда** записывается 0/1; `base[+0x14]` **всегда** читается по `0x9BE4`.

### A. Predicate = 1, путь `0x9BE8..0x9C3C`

- `0x9BE8: bt 26,0x9C40` **не** выполняется, потому что `predicate != 0`.
- `0x9BEC: cmpwi cr6,base[+0x14],0`; `0x9BF0: bf 26,0x9C84`: при **`base[+0x14] != 0`** прямой переход к общему return **без изменений счетчиков/state/global** после обновления `base+0x18`. Нет сброса противоположного счётчика в этом случае.
- При **`base[+0x14] == 0`**: `base[-0x04]++` по `0x9BF4..0x9BFC`; затем `cmplwi cr6,counter,3; bf 25,0x9C28` → при `counter <= 3` **не** проверяет внешний global.
- При **`counter > 3`**: `g=load32(0x8308D0F0)`; `cmpwi cr6,g,0; bt 26,0x9C28` → **только если `g != 0`**, `base[+0x10]=1` (`0x9C20`) и **`store32(0x8308D0F0,0)`** (`0x9C24`). Если global уже нулевой, этих двух записей нет.
- **Всегда**, когда `predicate=1` и `base+0x14=0`, `base[+0x00]=0` (`0x9C28..0x9C2C`), затем return через `0x9C30..0x9C3C`. Приращённый `base[-0x04]` здесь **не** сбрасывается.

### B. Predicate = 0, путь `0x9C40..0x9C90`

- `0x9BE8: bt 26,0x9C40` **выполняется**, если `predicate == 0`.
- `0x9C40: cmpwi cr6,base[+0x14],0`; `0x9C44: bf 26,0x9C84`: при **`base[+0x14] != 0`** сразу return, без изменений counters/state/global сверх более ранних writes.
- При **`base[+0x14] == 0`**: `base[+0x00]++` на `0x9C48..0x9C50`; `cmplwi cr6,counter,3; bf 25,0x9C7C` → если `counter <=3`, global не проверяется.
- При **`counter >3`**: `g=load32(0x8308D0F0)`; `cmpwi cr6,g,0; bf 26,0x9C7C` → **только если `g == 0`**, `base[+0x10]=2` (`0x9C74`) и **`store32(0x8308D0F0,1)`** (`0x9C78`). Если global ненулевой, этих двух записей нет.
- **Всегда**, когда `predicate=0` и `base+0x14=0`, `base[-0x04]=0` (`0x9C7C..0x9C80`), return через `0x9C84..0x9C90`. Приращённый `base[+0x00]` здесь **не** сбрасывается.

Таким образом, два различных условных изменения `0x8308D0F0` **не симметричны по guard**: `predicate=1, counter>3, g!=0` → `g=0,state=1`; `predicate=0,counter>3,g==0` → `g=1,state=2`. Не доказано, что другие writers не могут устанавливать глобальное слово в иные ненулевые значения. `base+0x14!=0` подавляет обе ветви инкремента и записи state, но **не** ранее сделанные sample/delta/predicate writes.

## 5. Связь setter → producer → callback: что известно

**[S: отдельный двухинструкционный setter, предоставленный как контекст]** `0x823A5730: stw r4,0x409C(r3); 0x823A5734: blr` — записывает 32-битное значение указателя из `r4` по адресу `r3+0x409C`. Указывается прямой callsite setter `0x8264D30C`; без полного анализа его caller здесь нельзя делать дополнительные выводы.

**[S: ранее описанный producer, без повторного разбора]** `0x823A4758` использует callback slot `object+0x409C` для косвенного вызова через `bctrl`. **Совпадение offset `0x409C` — прямое статическое согласование полей setter и producer**, но фактическое совпадение объектов и исполнение пути требуют дополнительных данных. В отличие от абстрактной возможности callback изменить предоставленный stack candidate, **конкретное тело `0x82649B68` не разыменовывает входной `r3` до его перезаписи**.

**[R: один 45-секундный exact-XEX Linux/GDB запуск]** Setter `0x823A5730` исполнялся со значением `r4=0x82649B68` для объекта с наблюдённой базой `0xB7365F00`; source-0 interrupt дошёл до consumer `0x823A4640`; sampled deferred indexes `object+0x413C/+0x4140` были `0/0`; breakpoints у candidate producer `0x823A4758` и callback entry `0x82649B68` не получили hits. Это данные **одного** ограниченного запуска, с остановками гостя от breakpoint. Не является доказательством, что static callers недостижимы или что callback никогда не вызывается.

**[I: условный registration-to-invocation вывод]** Если runtime `r3` в setter действительно равен объекту, который позднее producer использует как `object`, если slot не перезаписан и если producer достигает своего indirect `bctrl`, то `0x82649B68` — ожидаемый target. **Эти три условия не подтверждены совместной трассировкой**. Registration observed ≠ invocation observed. Нет основания обвинять scheduler/P-code/renderer или форсировать gate.

## 6. Один следующий конкретный target и неизвестное

**Следующий target: runtime entry `0x82649B68`.** На следующем **одном непрерывном run**, только read-only breakpoint/tracepoint, при фактическом hit зафиксировать `PC`, `LR`/return address, `r3` (producer candidate stack pointer), адрес объекта caller, значение `*(object+0x409C)` непосредственно у вызывающего косвенного callsite и thread/run ID. Сопоставить `object` с `0xB7365F00` из регистрации только внутри **того же** запуска, не с адресом другого процесса/запуска. Отсутствие hit при ограниченном окне должно так и оставаться ограниченным отрицательным наблюдением, а не выводом об unreachability. Это не требует изменения кода/retail semantics.

**Остаётся неизвестным:** назначение `0x821A7BA8` и адреса `0x83122BB0`; реальная семантика global words; временные единицы delta и происхождение selector; другие writers `0x8308D0F0`; наличие/количество runtime вызовов callback вне периода sampling; точная callee-сигнатура; действительно ли producer и setter используют один и тот же объект. **Граница доказательства:** статика устанавливает логику этой функции, контекст — совместимый registration slot, но не полную исполненную цепочку.
