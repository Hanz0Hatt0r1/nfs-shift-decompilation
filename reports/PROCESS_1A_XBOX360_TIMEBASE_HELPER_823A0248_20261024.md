# Process 1A — retail Xbox 360 timebase helper `0x823A0248`

**Дата:** 2026-10-24  
**Режим:** static report-only; никаких изменений кода, runtime или renderer/P2.  
**Границы:** `[0x823A0248, 0x823A0310)` (`0xC8` байт = **50 PPC-инструкций**), следующая function entry `0x823A0310`. Xbox 360 PPC big-endian.

## 1. Основание и уровни уверенности

**Входные идентификаторы (переданы, не пересчитывались здесь):**

- Retail `default.xex`, SHA-256: `8c86a34f369f9d064126342daccb2cfe4646cfe735df6a032812a40a9c0a2c58`.
- Live-memory-derived ELF, SHA-256: `2ffe352bda115285e58661cb5fc5ebe0a8c845d1e7a9ae07bee89e514636c00c`.

**[S] High confidence:** адреса, байты и ветвления из полного 50-инструкционного PPC-блока, данного в задании. **[E] Supplied ELF observation:** уточнённые пользователем байты константы по `0x820FFE40`; самостоятельного чтения ELF/пересчёта хешей в этом задании не производилось. **[R] Supplied runtime:** три раздельных Linux/GDB/Vulkan наблюдения; не смешиваются в общую временную последовательность. **[I] Inference:** вероятное назначение helper, типы структур, единицы измерения и связи с соседними функциями — гипотезы до дополнительных xrefs/trace.

## 2. ABI и структура данных

**[S]** Вход `r3 = record*` (32-битный указатель). Операция `lwz r10,0(r3)` извлекает **вложенный `object*`**, который не тождественен самому `record*`. Контекст по `r13` — **третья** независимая цепочка адресов: `thread_slot = *(u32*)(r13+0x100)`, `thread_value = *(u32*)(thread_slot+0x58)`. Для неё нет локальной проверки нулевого указателя. Название `thread` описывает происхождение через `r13`, но структура PCR/TLS, реальный thread ID и точный смысл поля данным блоком не удостоверены.

| Основание | Смещение | PPC доступ | Эффект |
| --- | ---: | --- | --- |
| `record = entry r3` | `+0x00` | `lwz` 32-bit, `0x0288` и `0x02B4` | извлечение `object*` **дважды**: до и после аккумулятора |
| `record` | `+0x04` | `lwz` 32-bit, `0x0254`, `0x0274`, `0x02D0` | нуль отключает всю рабочую часть; `==3` выбирает аккумулятор; значение передаётся в `r4` при callback |
| `record` | `+0x10` | `lwz` 32-bit, `0x0268` | в `r8`, участвует в вычислении `r6` |
| `record` | `+0x14` | `lwz` 32-bit, `0x0270` | сохранённая нижняя часть timebase; вычитается из текущего `mftb` |
| `*(u32*)(r13+0x100)` | `+0x58` | `lwz` 32-bit, `0x027C` | thread/context-derived слово; вычитается из `record+0x10` |
| `object` | `+0x5468` | `ld`/`std` 64-bit, `0x0290/029C` | 64-битный аккумулятор при `record[+4]==3` |
| `object` | `+0x5460` | `ld`/`std` 64-bit, `0x02A4/02B0` | 64-битный аккумулятор при `record[+4]!=3`, но `!=0` |
| `object` | `+0x347C` | `lwz` 32-bit, `0x02B8` | извлечение косвенного адреса функции в `r9` |
| `object` | `+0x5458` | `lfs` float32, `0x02C8` | множитель для FP-аргумента callback, только при ненулевом указателе `+0x347C` |

**[S]** Функция **не записывает** поля `record` или `r13`-контекста. Единственные записи в объект — `std` по одному из `object+0x5468` либо `object+0x5460`. `std r11,80(r1)` на `0x02D4` — отдельная 8-байтная запись **во временный stack slot**, не в объект.

**[S] Вызов/выход:** `mflr r12`, сохранение LR через старый SP по `-8(r1)`, кадр `0x60` байт (`stwu r1,-96(r1)`), восстановление в `0x0300..030C`. Единственный вызов — **`mtctr r9; bctrl`** на `0x02F0/0x02FC`: динамический target `*(u32*)(object+0x347C)`. Функция не присваивает константный return value на обоих путях без callback; на callback-пути `r3` после `bctrl` зависит от callback. Следовательно, **контракт возврата (в том числе void/не-void) не установлен**.

## 3. Условия и арифметика — пошагово

### 3.1 `record+0x04` gate

- `0x0254: lwz r11,4(r3)`; `0x0258: cmpwi cr6,r11,0`; `0x025C: bt 26,0x0300` → если **`record[4] == 0`**, сразу эпилог: **ни timebase-read, ни аккумулятора, ни callback**.
- Если значение ненулевое, `0x0260: mftb r11,268` считывает **низкую 32-битную часть архитектурного timebase (TBL)**. `slwi r11,r11,0` на `0x026C` не изменяет значение.
- `0x0278: sub r11,r11,r9` при `r9=record[+0x14]`. После `clrldi 32` (на `0x0294`/`0x02A8` и `0x02C4`) рабочее приращение:
  ```text
  delta32 = (TBL_low32 - record_u32[+0x14]) mod 2^32
  delta64 = zero_extend_u64(delta32)
  ```
  Следовательно, возможный wraparound TBL — арифметика по модулю `2^32`; из неё **не следует** длительность в миллисекундах без частоты TB и семантики saved snapshot.
- Отдельно `0x0284: sub r6,r8,r10` при `r8=record[+0x10]` и `r10=*(u32*)(*(u32*)(r13+0x100)+0x58)`. Результат **остаётся в `r6` до `bctrl`**. На PPC `sub` выполняется в GPR-разрядности, без явного 32-bit truncate в этом блоке. Это **не использованный в арифметике аккумуляторов** результат, но потенциально **регистровый аргумент callback**; трактовать его как dead code нельзя. Его единицы измерения не установлены.

### 3.2 Раздельные 64-битные аккумуляторы

`0x0274/0x0280/0x028C`: повторно `lwz r7,4(r3)`, `cmpwi cr6,r7,3`, `bf 26,0x02A4` (переход при **неравенстве**).

- **`record[4] == 3`:** `ld r9,0x5468(object)`; `clrldi r8,r11,32`; `add r9,r8,r9`; `std r9,0x5468(object)` (`0x0290..029C`).
- **`record[4] != 3` при уже проверенном ненуле:** `ld r8,0x5460(object)`; `clrldi r9,r11,32`; `add r9,r9,r8`; `std r9,0x5460(object)` (`0x02A4..02B0`).

Итог: **ровно один выбранный 64-битный аккумулятор** при каждом прохождении ненулевой ветви; сложение по модулю `2^64` (carry не обрабатывается отдельно). Данный блок не содержит синхронизации доступа к аккумуляторам/инструкций reservation/atomic. Тип «accumulated timebase ticks» — обоснованное описательное название операции, но фактические единицы и владельцы поля неизвестны.

### 3.3 Условный callback и float-путь

1. `0x02B4: lwz r10,0(r3)` — повторное чтение `object*`. `0x02B8: lwz r9,0x347C(r10)`; `0x02BC: cmplwi cr6,r9,0`; `0x02C0: bt 26,0x0300`. При **нулевом** указателе callback *пропускается*, но обновление одного аккумулятора **уже состоялось**.
2. При callback pointer `!=0`: `0x02C4: clrldi r11,r11,32`; `0x02C8: lfs f13,0x5458(object)`. `std r11,80(r1); lfd f0,80(r1); fcfid f0,f0; frsp f12,f0` (`0x02D4..02E4`) конвертирует zero-extended `delta32` как положительный signed 64-bit integer → float64 → float32.
3. **Исправление адреса константы (supplement пользователя):** `0x02CC: lis r10,0x8210` даёт `0x82100000`; `0x02E0: addi r11,r10,-560` даёт `0x820FFDD0`; `0x02E8: lfs f0,112(r11)` читает **`0x820FFE40`**, *не* `0x8210FD70`. По переданным байтам точного ELF `44 7A 00 00` (big-endian) это **`1000.0f`**. Эти байты **[E]** даны в уточнении; сам эффективный адрес **[S]** получается из PPC.
4. `0x02F4: fmuls f13,f13,f12`; `0x02F8: fmuls f1,f13,f0`, т.е. две последовательные операции float32 c промежуточным округлением:
   ```text
   f1 = f32( f32(object.float32[+0x5458] * f32(delta32)) * 1000.0f )
   ```
   Точный результат зависит от FP rounding/FPSCR и величин; физическую размерность **не назначаем**.
5. `0x02D0: lwz r4,4(r3)`; `0x02EC: li r3,0`; `0x02F0: mtctr r9`; `0x02FC: bctrl`. **Явно заданы при вызове** `r3=0`, `r4=record[+0x04]`, `f1=scaled_delta`, `CTR=callback`. Также до вызова сохранено `r6=record[+0x10]-thread_context[+0x58]`; сам callback может читать `r6` как аргумент, однако его сигнатура не установлена. Другие GPR не следует автоматически считать формальными аргументами на основании одного блока.

**Случаи:** `record[4]==0` → ни аккумулятор, ни вызов; `record[4]!=0`, callback null → аккумулятор, но нет вызова; `record[4]!=0`, callback nonnull → аккумулятор + FP-расчёт + косвенный вызов. Переходы `bt/bf 26` относятся к **CR6.EQ**, который выставляется указанными сравнениями.

## 4. Что подтверждено о xrefs и связи с wait predicate

**[S] Прямые calls:** внутри `0x823A0248..0x823A0310` нет инструкции `bl <retail-address>`; есть ровно **один косвенный `bctrl` в `0x823A02FC`**, target получен из `object+0x347C`. Внутренние branch targets: `0x823A02A4`, `0x823A02B4`, `0x823A0300`. Внутри блока нет сведений о **прямых вызывающих `0x823A0248`**; перечислять несуществующие найденные xrefs или угадывать динамический target нельзя.

**[R: переданный контекст]** Известен callsite `0x823A55B8 -> 0x823A0310`, **а не** `0x823A0248`. Факт смежной следующей entry `0x823A0310` **не создаёт callgraph edge**. В отдельном точном retail runtime main guest thread наблюдался в `0x823A0310` во время queue-predicate wait. Это свидетельствует о выполнении **другой** функции в том запуске; в данном block нет обращения к адресу `0x823A0310`, нет общей явно установленной структуры, не доказан call или timebase dependency между функциями.

**[R: отдельный 60-секундный запуск]** `0x823B33A0` — 27 вызовов; `object+0x2A9C` software queue tail `3→3003`; `0x831B3820=0`; predicate-byte samples `0x04/0x14`. Этот материал сам по себе **не** связывает эти события с рассматриваемым helper.

**[R: отдельный 45-секундный запуск]** source-0 callback дошёл до `0x823A4640`; `object+0x413C/+0x4140=0/0`; candidate producer `0x823A4758` не получил hits. Запуск **не** является продолжением предыдущего, scheduler bug не доказывается.

**[I] Связь с `0x823A0310`:** теоретически обе функции могут принадлежать одной подсистеме учёта времени/ожидания, но **ни этот disassembly, ни данные запуски не доказывают её**. Нельзя утверждать виновность Linux guest scheduler, PPC P-code, renderer или невозможность frontend progress только на данной основе. Не установлены: статические входящие xrefs, адрес и сигнатура callback, назначение селектора 3, механизм записи `record+0x14`, источник `record+0x10`, частота timebase, единицы `object+0x5458`, роль двух аккумуляторов и жизненный цикл record/object.

## 5. Один следующий конкретный retail target

**`0x823A02FC` — адрес инструкции `bctrl` рассматриваемой функции.** На **одном** read-only tracepoint здесь, в пределах **одного запуска**, снять `PC`, `CTR` и `*(record[0]+0x347C)`, `entry record` (сохранить при входе), `record+0x04/+0x10/+0x14`, `r3/r4/r6`, `f1`, `object+0x5458/+0x5460/+0x5468` и сохранённый caller return address/LR для идентификации исходного вызывающего участка. Это раскрывает **фактический retail callback target** и передаваемые значения, не предполагая заранее сигнатуру и не меняя выполнение. Если нужен **только статический** follow-up, сначала требуется получить retail xref к этой функции или разрешённый runtime target; по данному 50-инструкционному фрагменту адрес отдельной callback-функции назвать достоверно невозможно.

**Итог:** статически подтверждено селективное накопление `delta32` в одном из двух 64-битных полей вложенного объекта и условный вызов object callback с float32 величиной `delta32 * object[0x5458] * 1000.0f`; связь с `0x823A0310` остаётся непроверенной.
