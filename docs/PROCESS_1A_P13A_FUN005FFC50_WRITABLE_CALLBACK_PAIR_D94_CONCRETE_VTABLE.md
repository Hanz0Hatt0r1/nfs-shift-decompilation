# Process 1A / P1.3A — `+0xd94` concrete singleton vtable

The previous key-contract proof tied the `+0xd94` producer to `DAT_00c26058` but left vtable slot `+0xec` unresolved. This subset closes that target identity.

The retail image has exactly two direct writes to `DAT_00c26058`: `0x00823d1a` stores the object returned by constructor `0x008323d0`, and `0x00823d50` clears the singleton during shutdown. The object is allocated with size `0x3970`.

Constructor `0x008323d0` installs primary vtable `0x00b18d38`. Reading that file-backed vtable gives:

- slot `+0xe0` → `0x008313b0`;
- slot `+0xec` → `0x0082da60`.

`0x008313b0` allocates a registration entry into the singleton table at `+0x1ac8` and writes the selected table index through the caller's output pointer. Thus `0x00bbf2d4` is a table index/handle generated by the concrete registration implementation.

`0x0082da60` indexes the same table with `EDX`. A null table entry returns zero. A non-null entry loads that entry object's vtable slot 0 and dispatches to it with the three lookup arguments.

This proves the concrete `+0xec` target, but not yet the numeric range returned by every possible entry slot-0 implementation. Aggregate callback/P1.3 gates remain fail-closed.
