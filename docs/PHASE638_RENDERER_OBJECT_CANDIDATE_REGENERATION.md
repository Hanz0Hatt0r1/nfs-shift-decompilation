# Phase 638 — renderer OBJECT candidate regeneration from offline bootstrap

Phase 637 removed manual full shader-target and renderer-report handoffs from the
preferred offline renderer path. The remaining optional renderer handoff was:

```text
SHIFT.SGBRuntimeObjectCandidateJoin/1
```

Phase 638 regenerates that contract from artifacts already produced by the
resource bootstrap plus the Phase 630 capture pipeline regenerated from the
historical raw D3D9 JSONL.

No original game execution and no new capture are required.

## Vertical-slice blocker

The first playable Linux slice needs the resource and renderer paths to converge
without a manually curated scene-instance JSON. Repeated IMB placements can make
Phase 625 require an SGB OBJECT candidate set. Before Phase 638, the source-driven
renderer runner could only obtain that set from an external report bundle.

The preferred dependency chain is now:

```text
retail BFF/ZIP corpus
  -> OfflineRuntimeBootstrap
       -> OfflineNativeSceneBuild
            -> SGBScenePlacement
            -> SGBObjectRenderHandoffSet
            -> scene IR manifest

historical raw D3D9 JSONL
  -> Phase 630 raw bootstrap
       -> IMBRuntimeCapturePipeline

OfflineRuntimeBootstrap + regenerated IMBRuntimeCapturePipeline
  -> Phase 638 exact artifact resolver
       -> existing Phase 595 builder
            -> SGBRuntimeObjectCandidateJoin

Phase 638 optional join
  -> Phase 634 -> Phase 633 -> Phase 619-626 production
```

## Reused proof authority

Phase 638 does not implement a second scene or identity algorithm. It invokes the
existing:

```text
src/scene/sgb_runtime_object_candidate_join.py
```

The Phase 595 proof boundary is unchanged. For each runtime resource it still
requires exact capture-side archive/path/SHA identity, the same-instance gate,
and exact revalidation against the IR manifest before comparing the logical SGB
resource path.

A unique SGB candidate remains candidate evidence only. It is not automatically:

- portable resource identity;
- runtime OBJECT identity;
- render admission;
- world-transform proof.

## Exact offline-scene transport

The new helper is:

```text
tools/regenerate_renderer_object_candidate_join.py
```

It accepts:

- `SHIFT.OfflineRuntimeBootstrap/1`;
- `SHIFT.IMBRuntimeCapturePipeline/1` regenerated by Phase 630.

The bootstrap must report `offline_build_ready=true`. The helper resolves the
recorded native-scene and scene-IR artifacts and then requires:

- `SHIFT.OfflineNativeSceneBuild/1`;
- `static_resource_ready=true`;
- the recorded `scene_placement` artifact;
- the recorded `object_render_handoffs` artifact;
- exact SHA-256 agreement for both scene artifacts;
- `scene-ir/manifest.json`.

A hash mismatch, missing artifact, invalid format, or unavailable IR manifest
blocks regeneration. No basename fallback, archive-order choice, or replacement
resource is permitted.

## Optional unresolved result

`SHIFT.SGBRuntimeObjectCandidateJoin/1` is not required for every renderer run.
Phase 624/625 only needs it when repeated scene placements survive far enough to
require instance discrimination.

Therefore Phase 638 separates two states:

```text
source_ready = false
```

means the resource/capture evidence chain itself could not be proven and is a
fatal bootstrap error.

```text
source_ready = true
ready = false
```

means Phase 595 ran successfully but the current evidence did not produce a
fully usable candidate join. This is preserved as `optional-unresolved` and is
passed downstream as absence of the optional join. Phase 619-626 then decides
whether the repeated-instance gate actually requires it.

This distinction does not hide ambiguity: all Phase 595 blocking reasons remain
in the Phase 638 manifest.

## Bundle cross-check rule

When `--runtime-bootstrap` is supplied to the renderer self/source bootstrap,
Phase 638 becomes selection authority for the optional object join.

If a bundle also contains `SHIFT.SGBRuntimeObjectCandidateJoin/1`:

- a ready regenerated join is canonical-crosschecked against the bundle copy;
- an exact mismatch blocks;
- an unresolved regenerated join does **not** fall back to the bundle copy.

Thus an old manually prepared bundle cannot bypass a newer fail-closed result.

Without `--runtime-bootstrap`, the older bundle-optional compatibility path is
preserved.

## Source-bootstrap CLI

After producing a resource bootstrap, renderer production can consume it
without a manually supplied OBJECT candidate report:

```bash
python tools/run_silverstone_renderer_source_bootstrap_production.py \
  --capture-jsonl shift_d3d9_capture.jsonl \
  --pe-image SHIFT.exe \
  --corpus Silverstone_Era3_.zip \
  --corpus SHIFT_tail.zip \
  --runtime-bootstrap out/resource-bootstrap/runtime_bootstrap.json \
  --output-dir out/renderer-source-bootstrap
```

`SHIFT.exe` is used only as static PE bytes by the existing evidence path; it is
not launched.

The standalone Phase 638 diagnostic command is:

```bash
python tools/regenerate_renderer_object_candidate_join.py \
  --runtime-bootstrap out/resource-bootstrap/runtime_bootstrap.json \
  --capture-pipeline out/renderer/raw/imb_runtime_capture_pipeline.json \
  --output-dir out/object-candidate
```

## Generated artifacts

Phase 638 writes:

```text
renderer_object_candidate_regeneration.json
sgb_runtime_object_candidate_join.json
```

The regeneration manifest records resolved input paths, Phase 595 summary,
blockers, and the proof boundary. The join JSON is retained even when
`optional-unresolved` so the ambiguity frontier remains inspectable.

## Evidence boundary

Phase 638 explicitly does not:

- invent an SGB source archive identity;
- promote logical path uniqueness to runtime OBJECT identity;
- promote a candidate to render admission;
- rank candidates by frequency, address, or archive ordering;
- substitute a bundle result after a regenerated-source failure;
- infer missing capture events;
- request or execute a new capture.

The next blocker is whichever concrete requirement remains in the regenerated
Phase 619-626 renderer frontier after this optional handoff is removed. If that
frontier reaches a repeated placement and Phase 595 remains unresolved, its
specific missing witness must be reported rather than generalized into a new
capture request.
