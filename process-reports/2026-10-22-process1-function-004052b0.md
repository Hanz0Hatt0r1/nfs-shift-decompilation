# Process 1 — retail 0x004052B0: кандидат producer eEvent_EnterMainMenu

**Дата:** 2026-10-22  
**Исходник:** Need for Speed Shift PC retail 1.02, PE32, ImageBase 0x00400000, оригинальные `SHIFT.exe` и `SHIFT_objdump_full.txt`.  
**SHA-256, проверен по SHIFT.exe:** `eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1`.  
**Область:** статический retail-анализ producer и его непосредственных callee/caller, ограниченные пользовательские runtime-сведения v759/v760. Никаких изменений runtime-кода, полей, графических файлов; PR не создавался.

## Вывод

**0x004052B0 действительно содержит статически достижимый путь формирования события application-family 8 / code 3 и попытку передачи его в очередь приложения по `app+0x620`.** Однако успех allocation, прохождение через `0x004049D0` и сам факт вызова данного producer в v760 **не подтверждены runtime**.

**Исправление к прежней статической оценке reachability:** прямых `CALL rel32 0x004052B0` нет, зато в исходном retail PE установлен **прямой tail-`JMP 0x004052B0` на `0x0045C092`** внутри функции, начинающейся в районе `0x0045C000`. Конкретный прямой caller этой функции: **0x0046944D: call 0x0045C000**. Следовательно, **статическая цепочка вызова существует**: `0x0046944D → 0x0045C000 → 0x0045C092 → 0x004052B0`; достижимость и успешный enqueue в v760 это не доказывает. Место `0x0045C092` — прыжок без создания нового return address; обработчик получает ECX из `0x0040B870`.

## ABI 0x004052B0

| Компонент | Доказательство | Значение |
|---|---|---|
| ECX | `004052b5: lea esi,[ecx+0x620]` | this: указатель на application/owner |
| EDX | перезаписывается на `004052bd` | на входе не используется |
| stack args | `ret` в двух выходах; `[ebp+8]` не читается | нет явных входящих stack args |
| return | `AL=1` на `0x004052E1`, `AL=0` на `0x004052F2` | boolean признак выполнения двух стадий (allocation + acceptance) |
| ESI | сохраняется push/pop | callee-saved; остальные nonvolatiles не меняются |

MSVC x86 `__thiscall`-совместимая zero-stack функция объекта; исходная C++-декларация и имена методов без символов недоказуемы. Старшие 24 бита EAX **не нормализуются**: используется только AL.

`ESI=app+0x620` — указатель **встроенного объекта очереди событий**, а не сам app. Для известного runtime owner `0x00BBF960` это **0x00BBFF80**. Конструктор/жизненный цикл queue-family и consumer в прошлом отчёте подтверждают роль поля; точное исходное C++ имя queue class не требуется для ABI этой функции.

## Вызов 0x0045B530: фактическая allocation-процедура

`0x0045B530` — короткий **tail-jump `jmp 0x005039A0`**; функциональная реализация находится по `0x005039A0`.

Из нашего блока:
```asm
004052bb  push 0
004052bd  lea edx,[ebp-4]
004052c0  mov ecx,esi
004052c2  call 0x45b530
004052c7  test al,al
004052c9  je 0x4052f2
```
Фактический ABI аллокатора: `ECX=queue`, `EDX=&localEventPtr`, **один stack DWORD 0**; callee `0x00503A37 / 0x00503AC2` заканчивается `ret 4`. Аргумент 0 передаётся внутрь `0x00633290` как metadata/size-like аргумент, точное исходное имя не доказано.

В `0x005039A0–0x00503AC2`:
- `0x005039FB` записывает ноль в `*outEvent`.
- `0x005039F4` устанавливает `EDX=0x0C`, `0x00503A01` вызывает `0x00633290`, запрос **12-байтового** объекта. Если результат `EAX=0`, путь **`0x00503A2F–0x00503A37` возвращает `AL=0`**. Отсутствует последующая попытка enqueue из `0x004052B0`.
- При ненулевом результате: `0x00503A59` вызывает `0x006327B0` для инициализации выделенной памяти; `0x00503A74` записывает vptr **0x00ABFC10** в начало объекта; `0x00503A7A` вызывает `0x00632FF0` для привязки к queue; `0x00503A8E` присваивает `*outEvent=allocatedEvent`; `0x00503ABC` возвращает `AL=1`. Возвращаемое значение от `0x00632FF0` не тестируется данным кодом отдельно.
- `0x00633290` получает ECX=queue, EDX=12, stack DWORD=0, вычисляет объём с служебной областью и выделяет объект через memory subsystem; на failure возвращает ноль, на success возвращает pointer на данные. Утверждение «выделение удалось» подтверждается только для ветви AL=1, **не** для конкретного v760.

Блок `0x004052B0` по ветви AL=1 сразу читает DWORD localEventPtr. Здесь нет самостоятельной проверки его non-null; контракт `0x005039A0` обеспечивает pointer при нормальном успешном результате.

## Заполнение event и acceptance в 0x004049D0

После allocation success:
- `0x004052CB`: `EDX=[EBP-4]` = event pointer;
- `0x004052D0`: `BYTE [event+5] = 8` (**event-family**);
- `0x004052D4`: `BYTE [event+4] = 3` (**code**);
- `0x004052D8`: `call 0x004049D0`, с `ECX=queue`, `EDX=event` и без стековых аргументов.

Из `0x004049D0` (начало и tail переход через `0x00471E6C` — **не путать этот compiler split с новой функций**):
- `queue+0x25C == 0` на `0x00404A09` → **AL=0** на `0x00404A24`, без enqueue.
- Если `[queue+0x250]&2`, вызывается `[queue.vtable+0x08](queue,event)` на `0x00404A34–0x00404A3D`; результат здесь не проверяется.
- `0x00404A3F` вызывает `0x00632FE0` с `ECX=event`, проверяет принадлежность/owner против queue. Если `EAX==queue`, **0x00404A4F** вызывает `0x006333F0`, фактически включающий event в linked queue, затем main path возвращает `AL=1` через `0x00404AC8` или `0x00404A69`.
- Если owner не совпадает, `0x00404A70–0x00404AA0` пытается выделить новый event через `0x0045B530`, при ошибке возвращает `AL=0`, при успехе `0x00404AA6` копирует/инициализирует event через `0x00403D00`, и `0x00404AB0` помещает новый объект в очередь. Эта ветвь может return `AL=1` без постановки **самого первоначального pointer**, но с постановкой его логического эквивалента.
- На основных путях успешного включения `0x004049D0` возвращает `AL=1`; таким образом `0x004052B0` считает операцию принятой, но не проверяет, был ли обработан event в consumer.
- Точные подробности queue sync `+0x250` и owner/clone ветви приводятся как реальные условия, но исходные поля/компиляторский API не восстановлены. В частности, нельзя по одному AL утверждать, что consumer уже вызван.

### Cleanup при отказе

При **allocation fail** управление сразу переходит на `0x004052F2` и возвращает AL=0, **без** вызова `0x004C7150`, так как `*outEvent` установлен в ноль аллокатором.

При **enqueue reject** (`AL=0` от `0x004049D0`) управление на `0x004052E8` передаёт `ECX=queue`, `EDX=&localEventPtr` в `0x004C7150`. Эта функция при non-null `*out` вызывает event.vtable+0 с аргументом 0 на `0x004C7192`, затем `0x00632FB0(queue,event)` на `0x004C7198`, обнуляет DWORD `*out` на `0x004C719D`. То есть **release/cleanup локально созданного event**, а не «отмена уже принятого события»; владение клоном при других ветвях нельзя описывать без анализа всех путей.
При успехе (`0x004052E1`) локальное освобождение не вызывается: event принадлежит успешному пути передачи.

## Точная статическая цепочка достижимости

**Есть прямой tail-JMP, отсутствующий в прежнем поиске только CALL rel32.**

```asm
0046944d: e8 ae 2b ff ff   call 0x45c000
...
0045c07c: mov ecx,[edi+0xc4c]
0045c084: mov eax,[edx+0x48]
0045c087: call eax
0045c089: call 0x40b870
0045c08e: pop edi
0045c08f: mov ecx,eax
0045c091: pop esi
0045c092: e9 19 92 fa ff   jmp 0x4052b0
```

`0x0040B870` — singleton app getter/initializer, загружает адрес **0x00BBF960** (например, 0x0040B883) и возвращает объект; на последнем tail-JMP `ECX` берётся именно из EAX getter. `0x0045C000` до перехода делает внешние проверки (0x0045C006..0x0045C087); некоторые из них инициируют side effects, однако **нормальный путь до конца** действительно обязательно входит в `0x004052B0`. Переход `jmp`, а не `call`, означает отсутствие нового return address; вызов может визуально отображаться как frame `0x0045C000` в обратной трассе.

Отсутствие direct `CALL` не равно отсутствию статического пути. Обнаруженное ребро `0x0045C092` **не доказывает выполнения caller 0x0046944D в v760**, не исключает дополнительные indirect-кандидаты и не является доказательством успешного enqueue.

## Сопоставление с consumer / v760

Consumer `0x00405DA0` получает queue `app+0x620` и по событию с `event+5=8` и `event+4=3` выбирает application-family/code 3, ветвь `0x00405ED1` и callback **0x00403C60** (в retail diagnostic string это `eEvent_EnterMainMenu`). Это **совпадение формата и конкретного callback**, а не runtime факт.

v760: в bounded 360-frame capture-mode trace было **1127 вызовов** virtual pop `0x00633370` из consumer `0x00405DA0`, у наблюдаемых pop EAX=0; receiver **0x00BBFF80**, `[queue+4]=[queue+8]=0`; exit 0, validation_errors=0; выбранные Draw/DrawUP импорты не наблюдались. **Этот trace не охватывает entry `0x004052B0` или результат `0x004049D0`**. Следовательно, нельзя утверждать, что producer исполнился/не исполнился, что enqueue успешно завершился, или что отсутствие menu/draw вызвано конкретным queue gate. v759 отдельно завершился ранним unsupported managed texture description; он не эквивалентен v760 без capture-mode и не служит измерением producer reachability.

## Confidence / exclusions

**Прямо доказано retail:** hash, ABI, subobject queue pointer, AL-return paths, vptr allocation и output pointer, заполняемые два byte-поля event, входные регистры acceptance, rejection cleanup; наличие direct JMP 0x0045C092 и CALL 0x0046944D на обрамляющую функцию; соответствие кодов dispatch consumer.

**Сильная интерпретация:** `0x004052B0` — producer `eEvent_EnterMainMenu`; `0x004049D0` — accept/enqueue, а `0x0045B530` — allocation 12-byte event. Тип queue/Event original source-level не установлен по символам, хотя структура и logging подтверждены.

**НЕ доказано:** исполнение producer именно в v760, AL успешных allocation/acceptance в этом прогоне, единственность producer пути, достижение главного меню, причинная связь с draw, эквивалентность capture-mode production runtime.

## Следующий один retail trace target

**0x0045C092** — прямой tail-JMP к producer, который устраняет сомнение в статическом графе. При точечной трассировке entry этого адреса записать ECX/EAX перед JMP, caller stack, затем факт достижения `0x004052B0`, AL аллокатора `0x0045B530` и AL acceptance `0x004049D0`. Никакого forcing поля/patch не требуется. Это единственный предлагаемый следующий адрес.
