# Process 1 — retail 0x0082F710: CRenderer::BeginFrame

**Date:** 2026-10-22  
**Scope:** static retail PE / full objdump plus the user-supplied v730 runtime-provenance observation. **No source edits; no PR.**  
**Binary:** Need for Speed Shift, retail PC 1.02, PE32 x86, image base 0x00400000.  
**SHA-256:** `eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1` — independently checked against the provided /mnt/data/SHIFT.exe.

## Verdict

**0x0082F710 is the retail `CRenderer::BeginFrame` method**, identified by the exact UTF-16 string at 0x00B18028 passed to imported `D3DPERF_BeginEvent`, its renderer vtable position and the paired `CRenderer::EndFrame` entry. It resets a streaming-buffer offset **even when the rendering device is absent**. With a non-null device pointer it clears a cached state, updates a numeric renderer field, enters a D3DPERF marker, conditionally resets three subordinate-object flags, sets **BYTE [renderer+0x694] = 1 independently of the virtual method's AL result**, closes the marker, and returns AL=1.

The v730 observation (flag 0 at earlier 0x008353E0 calls around dispatch 432k, the last observed writer 0x0082F710 near dispatch 1,304,810, flag 1 at later calls) is consistent with these instructions. **Dispatch counts do not establish rendering causality, a draw event, or an underlying reason for no Draw*.**

## Exact ABI / function contract

- **ECX**: pointer to renderer object (`this`), copied to ESI at **0x0082F711**.
- **EDX**: *not an argument consumed by this body*. It is set to 0 at **0x0082F72A** and supplied to `0x0082E510`.
- **Stack arguments**: none; both returns are plain `ret` (**0x0082F729**, **0x0082F771**).
- **Convention**: compatible with MSVC x86 `__thiscall` member method. More specifically, ECX carries `this`, caller passes no parameters; virtual dispatch confirms member-method usage.
- **Return**: `AL=0` if device-pointer field is null, `AL=1` if the non-null path returns normally. This is a byte-sized boolean contract. `EAX` is **not normalized** to DWORD 0/1 (both exit paths write only AL).
- **Nonvolatiles**: ESI is saved/restored. EAX/ECX/EDX may be clobbered by calls.
- The return does **not** incorporate `0x0082E510`'s result, `0x0082F3D0`'s result, the virtual method's result, `0x00850320`'s result, or Direct3D event return values.

## Main control flow with exact addresses

1. **0x0082F710–0x0082F713**: save ESI and form `this=ECX`; `cmp DWORD [ESI+0x478],0` is the only early-exit gate in this body.
2. **0x0082F71A**: `mov DWORD [ESI+0x1F78],0` is *unconditional*, before `jne`. The instruction `mov` does **not** change flags; the JNE at **0x0082F724** branches on the preceding CMP at **0x0082F713**. This ordering matters.
3. **0x0082F726–0x0082F729**: if `[ESI+0x478]==0`, `xor al,al; pop esi; ret`. No `+0x694` write here; its prior value is retained by this body.
4. **0x0082F72A–0x0082F72C**: `xor edx,edx; call 0x0082E510` with ECX still pointing at renderer.
5. **0x0082F731–0x0082F733**: restore ECX from ESI, call `0x0082F3D0`.
6. **0x0082F738–0x0082F742**: `push 0x00B18028; push 0xFFFF0000; call 0x00923628`. It calls `D3DPERF_BeginEvent` with color 0xFFFF0000 and UTF-16 label `CRenderer::BeginFrame`.
7. **0x0082F747–0x0082F751**: `ECX=[ESI+0x5F4]`; `EAX=[ECX]` (vptr); `EDX=[EAX]` (vtable slot 0); `call EDX` with subordinate object's `this` in ECX.
8. **0x0082F753–0x0082F755**: `test al,al; je 0x0082F762`.
9. **0x0082F757–0x0082F75D**: only when virtual AL != 0, call `0x00850320` with ECX reloaded from `[ESI+0x5F4]`.
10. **0x0082F762**: `mov BYTE [ESI+0x694],1`. Both outcomes of `test al,al` reach this instruction; it does **not** depend on virtual AL. Assumes the callees return normally and pointers are valid; `+0x5F4` is **not** separately null-checked.
11. **0x0082F769**: call `0x00923622` = `D3DPERF_EndEvent`.
12. **0x0082F76E–0x0082F771**: `mov al,1; pop esi; ret`.

## Retail corroboration from neighboring functions and data

### Method identification and pairing

- Constructor path **0x008323EB** installs renderer primary vtable **0x00B18D38** at `[ESI]`; **0x008323F1** also installs secondary vtable 0x00B18D14 at `[ESI+4]`.
- In primary vtable 0x00B18D38: slot offset **+0x12C** (table entry at **0x00B18E64**) contains **0x0082F710**; next slot **+0x130** (entry at **0x00B18E68**) contains **0x00835D80**.
- `0x00B18028` in .rdata is the verified UTF-16 string **`CRenderer::BeginFrame`**, not an invented symbol.
- Call stub **0x00923628** jumps through `[0x00AA65E4]` imported from `d3d9.dll!D3DPERF_BeginEvent`. **0x00923622** jumps via `[0x00AA65E0]` to `d3d9.dll!D3DPERF_EndEvent`.
- Paired EndFrame method **0x00835D80** uses UTF-16 string `CRenderer::EndFrame` at **0x00B19268**, enters D3DPERF at **0x00835DEA**, calls through device vtable +0x44 at **0x00835E7C**, **clears BYTE [ESI+0x694]=0 at 0x00835E86**, then handles queues at **0x00835E98** via `0x00835590`, ending its D3DPERF event at **0x00835E9D**. EndFrame also returns early if `+0x478` is zero (**0x00835DCD–0x00835DDD**). This is strong static evidence that `+0x694` represents the **in-frame / begun-frame phase** in these methods, not proof that any drawing occurs.

### Why +0x1F78 is reset

- In **0x00830E70** (a separate renderer method), **0x00830E77** reads DWORD `[renderer+0x1F78]`; **0x00830E81–0x00830E89** compares current offset plus requested size `[EBP+0x10]` against capacity `[renderer+0x1F74]`. On overflow it calls `0x00857960` and sets `+0x1F78=0` at **0x00830E90**.
- **0x00830EA0** passes the offset to a buffer's vtable method at `+0x2C` (0x00830EC2–0x00830EC5), followed by another vtable call at `+0x30` (0x00830EDE–0x00830EE5). **0x00830EF7–0x00830F0A** supplies the current offset, buffer pointer `[renderer+0x1F70]`, stride `0x40`, and a stream argument to a device vtable method at `+0x190`. **0x00830F0C** advances `[renderer+0x1F78]` by the requested byte count.
- Hence **confirmed field role**: DWORD `+0x1F78` is a byte cursor/offset for a capacity-bounded streaming resource; DWORD `+0x1F74` is its limit; DWORD `+0x1F70` is the associated buffer-like interface pointer. A dynamic vertex-buffer/stream interpretation is strongly supported by Direct3D-like call signatures, but the precise resource type should not be derived solely from the 0x0082F710 body.
- The zero at **0x0082F71A** resets that cursor even on the early `AL=0` exit. It **does not** reset the buffer memory itself, all renderer state or a draw counter.

### What 0x0082E510 and 0x0082F3D0 do

- `0x0082E510` takes `ECX=renderer`, `EDX=new value`; compares with `[renderer+0x70C]` at **0x0082E516**. With **EDX=0** from our caller, a nonzero previous value executes **0x0082E53F: mov [EDI+0x70C],ESI**, storing zero; if already zero it returns via **0x0082E545**. The callee's device-vtable invocation at **0x0082E534** lies under `test ESI,ESI` (**0x0082E51E–0x0082E520**) and is **not entered** for EDX=0 on this path. Thus it clears a cached binding/state slot `+0x70C`, but the type of that state is not proven here. Its boolean return is ignored.
- `0x0082F3D0` reads/computes a numeric value: it calls `0x0040F0D0` with ECX = `renderer+0x6EC` at **0x0082F3DD**, performs integer-to-float conversion and floating operations, and finally writes FLOAT `[renderer+0x708]` at **0x0082F40F**. The exact physical units and semantic name require analyzing the timer/helper and constants; simply calling it "time" is an interpretation.

### Virtual method via renderer+0x5F4; conditional 0x00850320

- Constructor path allocates **0xDC** bytes and calls **0x00850190** (**0x00832802–0x0083281A**), stores the resulting pointer to `[renderer+0x5F4]` at **0x00832823**.
- Within `0x00850190`, **0x00850244** writes the derived vtable pointer **0x00B1BD88** to the subordinate object's first DWORD; **0x008501AF** initializes BYTE `[child+5]=0`.
- Exact vtable slot **[0x00B1BD88+0]=0x006A7300**; `0x006A7300: mov al,BYTE [ecx+5]`; `0x006A7303: ret`. So on the constructed class the vcall at 0x0082F751 **reads BYTE [child+5]**. Its value is a per-child predicate; exact original name is not established. Another routine, **0x006A7310**, stores to `[ECX+5]` at **0x006A7316**, corroborating that the field is mutable.
- If that getter's AL != 0, **0x00850320–0x0085032D** executes:
  - **0x00850320:** `xor al,al`
  - **0x00850322:** `mov BYTE [ecx+7],al`
  - **0x00850325:** `mov BYTE [ecx+8],al`
  - **0x00850328:** `mov BYTE [ecx+9],al`
  - **0x0085032B:** `mov al,1`; **0x0085032D:** `ret`.
- It clears **child+7/+8/+9**, not `renderer+0x694`, and does not clear child+5. These are subordinate state bytes; their precise meanings are not established by the getter and reset alone.
- A non-null device `[renderer+0x478]` does not logically guarantee that `[renderer+0x5F4]` is non-null or that its vtable remains the constructor's vtable. The observed normal behavior requires valid subordinate state.

### +0x694 is a frame-phase flag used by 0x008353E0

- Renderer initialization **0x00832560** sets BYTE `[renderer+0x694]=0`.
- `0x0082DBB0: mov al,BYTE [ecx+0x694]; ret` is a byte getter. In the renderer primary vtable its entry is at **0x00B18E6C**, slot **+0x134**.
- The separate routine **0x008353E0** invokes `[renderer.vtable+0x134]` at **0x0083540D–0x00835417** and tests AL at **0x00835419**. If true, **0x0083541D–0x00835426** prepares a queue at `renderer+0x1E80` and calls `0x004CB900` to append the supplied item. If false it continues into direct item processing at **0x00835434**. The function has a preliminary branch **0x008353F8–0x0083540C** checking a separate object's `+4` reference-like field; not all calls necessarily reach the getter.
- This establishes **static control-flow relevance** for the user-reported v730 reads: the frame-phase flag gates deferred versus immediate handling on that path. It does *not* prove GPU draw submission or provide the reason for no Draw*.

## Runtime provenance (user-supplied v730 evidence, not separately re-executed)

- During v730, BYTE `[0x2002B698+0x694]` = BYTE `[0x2002BD2C]` was 0 at reported earlier `0x008353E0` invocations near dispatch 432k.
- The most recent/last observed writer in that provenance record was **0x0082F710**, with transition to 1 around dispatch **1,304,810**.

- These facts are **consistent** with the unconditional main-path store at `0x0082F762` and virtual getter `0x0082DBB0`. They do not establish exact frame timing, number of renders, draw readiness, a particular CPU/GPU event, or causation of missing guest Draw*.

## Confidence / limitations

**Direct binary evidence:** hash; ABI register usage and RET; unconditional reset of DWORD +0x1F78; one early-exit predicate +0x478; actual +0x1F78 consumer / offset arithmetic; +0x70C update on EDx=0; +0x708 numeric write; Begin/End markers and imports; subordinate vtable 0x00B1BD88 slot 0x006A7300 getter child+5; conditional child+7/8/9 reset; +0x694 write after both virtual outcomes; EndFrame zeroing; renderer flag getter and conditional queue path in 0x008353E0.

**Supported interpretation:** `CRenderer::BeginFrame` and `EndFrame` are frame-phase methods; +0x694 is frame-open state; +0x1F78 is a streaming-buffer offset.

**Unproven / must not overstate:** source-level exact C++ field names, specific semantics of child+5/+7/+8/+9, guaranteed valid child pointer with device non-null, what `0x0040F0D0` timing units represent, successful draw or Present based merely on BeginFrame, relationship between dispatch counts and actual GPU activity, causal explanation of absent Draw*.
