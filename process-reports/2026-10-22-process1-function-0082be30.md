**Дата:** 2026-10-22  
**Бинарник:** Need for Speed Shift retail PC 1.02, PE32 x86, image base 0x00400000.  
**SHA-256:** `eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1` — проверено непосредственно по `SHIFT.exe`.  
**Основания:** байты retail EXE, полный `SHIFT_objdump_full.txt`, специально предоставленный блок, ранее зафиксированные пользовательские сведения v728/v733/v734/v735. Последние *не перепроверялись* запуском. Статические адреса приведены как retail VA. Работа исключительно аналитическая: исходники не изменялись, PR не создавался.

## Краткий вывод

`0x0082BE30` — виртуальный метод объекта семейства `CMaterial`, находящийся в vtable **0x00B178C8 по смещению +0x60** (DWORD по **0x00B17928**). `0x0082A770` на **0x0082A789** устанавливает на конструируемый объект эту vtable. Метод заменяет ссылочный 32-битный указатель в индексируемом участке данных материала.

Контракт: **ECX=material, EDX=unsigned index, [ESP+4]=new item pointer** (в прологе это `[EBP+8]`). Возврат `AL=0` при индексе вне диапазона, `AL=1` при штатной замене. Сначала проверяется `index < count` по беззнаковому сравнению; при ошибке вызывается setter статуса renderer с кодом 4. При допустимом индексе возможна инвалидация кэша, старый указатель обрабатывается через renderer vtable `+0x238 → 0x008353E0`, новый (если не NULL) получает инкремент `[new+4]`, затем DWORD слота заменяется на `new`.

Это **операция управления материалом и ссылками**, не прямой Draw*, Present или вызов GPU API. Точная функциональная классификация объекта, чей адрес хранится в слоте, зависит от дескриптора [material+0x0C] и не подтверждается одним блоком.

## 1. ABI и return-пути

- **0x0082BE34** `mov esi,ecx`: `this=material`.
- **0x0082BE3C** `mov edi,edx`: `EDX` на входе — **индекс слота**, а не количество слотов, длина буфера или pointer. `EDI` сохраняет индекс через виртуальные вызовы.
- **0x0082BE92** `mov ebx,[ebp+8]`: явный стековый аргумент — **новый DWORD/указатель**, допускается 0.
- **0x0082BE61** и **0x0082BEB3**: `ret 4`, callee удаляет **один DWORD стекового аргумента**. `EBP/ESI/EDI` сохраняются; `EBX` сохраняется только на ветви, где используется.
- Результат — **`AL` boolean**: **0x0082BE5D** `xor al,al` при отказе; **0x0082BEAF** `mov al,1` при успехе. Старшие 24 бита `EAX` не нормализуются; интерпретация полного DWORD как 0/1 не гарантирована.
- ABI-реконструкция: MSVC x86 `__fastcall`-совместимый member-like вызов с тремя логическими параметрами (`this`, индекс, новый указатель). Точное исходное объявление C++ без символов недоказуемо. На уровне машинного кода регистры, стек и размер `ret` определены точно.
- Ни входного `AL`, ни выходного `EDX` интерфейс не требует: `EDX` используется сначала как index, затем перезаписывается адресами virtual methods/oldItem.

## 2. Виртуальный count и беззнаковая граница

~~~asm
0082be36: mov ecx,DWORD PTR [esi+0xc]
0082be39: mov eax,DWORD PTR [ecx]
0082be3e: mov edx,DWORD PTR [eax+0x34]
0082be41: call edx
0082be43: cmp edi,eax
0082be45: jb 0x82be64
~~~

Контракт внутреннего виртуального метода: `ECX=*(material+0x0C)`, `vtable+0x34` без дополнительных параметров, возвращает в `EAX` **число доступных индексируемых элементов**. Основание: использование этого результата как exclusive верхней границы на **0x0082BE43–0x0082BE45** и аналогичные циклы в `0x0082A770`/`0x0082A690`. Нельзя утверждать конкретное исходное имя (например, shader stage count, constant count или texture count) без реализации виртуального метода дескриптора. Сам vptr объекта `[material+0x0C]` данным блоком не разрешён.

`jb` — **unsigned** `index < count`; `index == count`, больше или представленный как отрицательный 32-bit индекс 0xFFFFFFFF уходит в ошибку. В отличие от уже изученной функции `0x008353E0` тут нет signed `jle`.

## 3. Ошибочная ветвь: точное значение EDX=4

~~~asm
0082be47: mov ecx,DWORD PTR ds:0xc26058
0082be4d: mov eax,DWORD PTR [ecx]
0082be4f: mov eax,DWORD PTR [eax+0x2e8]
0082be55: mov edx,0x4
0082be5a: call eax
0082be5d: xor al,al
0082be61: ret 0x4
~~~

Глобальный `[0x00C26058]` — указатель на основной объект renderer (по его основной vtable **0x00B18D38**). Слот `+0x2E8` в этой vtable расположен по **0x00B19020**, содержит **0x0082E740**:

~~~asm
0082e740: mov DWORD PTR [ecx+0x5e4],edx
0082e746: ret
~~~

В результате при штатном renderer vptr неверный индекс приводит ровно к **DWORD [renderer+0x5E4] = 4**. Парный getter `0x0082E730: mov eax,[ecx+0x5E4]; ret` подтверждает, что это поле отдельного извлекаемого статуса. Термин «код ошибки индекса» — оправданная контекстная интерпретация, а имя перечисления для числового 4 не установлено. Это *не* подтверждённый exception, лог, D3D вызов или остановка процесса.

Ошибочная ветвь не входит в обработчик старого pointer, не увеличивает refcount нового, не меняет слот и заканчивается `AL=0`.

## 4. Структура material +0x0C/+0x14/+0x18

Ключевые поля:

| Смещение относительно material | Подтверждение | Значение |
| --- | --- | --- |
| +0x00 | 0x0082A789 / 0x00B17928 | vtable материального объекта `0x00B178C8` |
| +0x04 | 0x0082A77E–0x0082A781 | отдельное refcount-подобное поле; **не** указатель слота |
| +0x0C | 0x0082BE36; 0x0082A797–0x0082A79A | pointer на интерфейс/дескриптор раскладки с виртуальным count |
| +0x14 | 0x0082BE71, 0x0082BEA1 | pointer на массив DWORD **байтовых смещений** |
| +0x18 | 0x0082BE77, 0x0082BEA4 | **базовый pointer** на непрерывный блок данных |
| +0x1C | 0x0082A7AB, 0x0082A824, 0x0082A840–0x0082A878 | отдельный массив записей по 12 байт, не выбранный основным setter |

Точное вычисление адреса в обеих ветвях replacement:

~~~asm
0082be71: mov ecx,[esi+0x14]
0082be74: mov edx,[ecx+edi*4]  ; offset[index]
0082be77: mov eax,[esi+0x18]  ; byte buffer base
0082be7a: mov edx,[edx+eax]    ; old = DWORD at base + offset[index]
...
0082bea1: mov ecx,[esi+0x14]
0082bea4: mov eax,[esi+0x18]
0082bea7: mov edx,[ecx+edi*4]
0082beaa: mov [edx+eax],ebx    ; DWORD at base + offset[index] = new
~~~

То есть `slotAddress = (BYTE*)material.field18 + DWORD(material.field14 + 4*index)`. Указатель `+0x14` не является массивом значений-указателей; он указывает на **таблицу относительных байтовых смещений**. Слоты неодинакового размера возможны; `index*4` адресует таблицу, а не вычисляет смещение поля данных как `base+index*4`.

Конструктор `0x0082A770` (создаваемый фабрикой `0x0082DEE0` на **0x0082DEF4**) копирует дескриптор `[source+0x0C]` в `[material+0x0C]` на **0x0082A797–0x0082A79A**, заполняет `+0x14,+0x18,+0x1C` нулями на **0x0082A7A5–0x0082A7AB**, затем:
- **0x0082A890–0x0082A8C5:** получает count из descriptor.vtable+0x34 и в цикле суммирует `descriptor.vtable+0x40(index)` для расчёта общего размера blob.
- **0x0082A8C7–0x0082A8EC:** выделяет `count*4` байт для `+0x14` и сумму размеров для `+0x18` через `0x008868C0`.
- **0x0082A8EF–0x0082A910:** `0x009042E0` копирует исходные таблицу смещений и blob из `source+0x14`/`source+0x18`.
- **0x0082A928–0x0082A951:** в цикле, для элементов, тип которых выдаёт `descriptor.vtable+0x3C(index)` как **0x10**, проверяет pointer в соответствующем DWORD blob и увеличивает `[pointer+4]` через `0x00839E20`. Это поддерживает интерпретацию типа 0x10 как ссылочного pointer-элемента. Исходный enum/name для 0x10 не установлен.

Два других метода той же vtable: **0x0082BEC0** расположен по `0x00B17924` (`material.vtable+0x5C`), при том же индексировании записывает сырой DWORD, **без** предварительной обработки old/refcount new, тогда как `0x0082BE30` по `+0x60` — refcount-aware replacement. Это различие реальное; их исходные имена не доказаны.

## 5. Инвалидация кэша при special material

~~~asm
0082be64: cmp esi,DWORD PTR ds:0xc26174
0082be6a: jne 0x82be71
0082be6c: call 0x82a630
~~~

Если объект совпадает с кэшированным глобальным `[0x00C26174]`, выполняется `0x0082A630`. Его тело:

~~~asm
0082a630: xor eax,eax
0082a632: mov DWORD PTR ds:0xc26174,eax
0082a637: mov DWORD PTR ds:0xc26178,eax
0082a63c: jmp 0x83a6f0
0083a6f0: jmp 0x83a4f0
0083a4f0: mov DWORD PTR ds:0xb8e418,0x3
0083a4fa: ret
~~~

Следовательно, **три глобальных записи**: кэшированный material-pointer = 0, сопутствующее cached значение = 0, глобальная переменная `[0x00B8E418]=3`. Подтверждена инвалидация кэша состояния, а точное имя глобального `0x00B8E418` и семантика числового 3 требуют отдельной проверки. Инвалидация происходит **после успешной проверки индекса, но до чтения старого pointer**; на неверном индексе она не происходит.

В соседнем методе `0x0082A690`, связанном с UTF-16 маркером `CMaterial::SetShaderState` по **0x00B179C0**, используются те же `[material+0x0C]`, layout и глобальные cached `0x00C26174/0x00C26178`. Это контекст material/shader-state, но не доказательство Draw* для `0x0082BE30`.

## 6. Замена ссылки и достижимость renderer-release

~~~asm
0082be71: mov ecx,[esi+0x14]
0082be74: mov edx,[ecx+edi*4]
0082be77: mov eax,[esi+0x18]
0082be7a: mov edx,[edx+eax]
0082be7d: test edx,edx
0082be7f: je 0x82be91
0082be81: mov ecx,DWORD PTR ds:0xc26058
0082be87: mov eax,[ecx]
0082be89: mov eax,[eax+0x238]
0082be8f: call eax
0082be91: push ebx
0082be92: mov ebx,[ebp+0x8]
0082be95: test ebx,ebx
0082be97: je 0x82bea1
0082be99: lea ecx,[ebx+0x4]
0082be9c: call 0x839e20
0082bea1: mov ecx,[esi+0x14]
0082bea4: mov eax,[esi+0x18]
0082bea7: mov edx,[ecx+edi*4]
0082beaa: mov [edx+eax],ebx
~~~

- Старый pointer сначала получается как **DWORD** из вычисленного адреса. Если равен 0, вызова renderer нет.
- При non-null old, `ECX=[0x00C26058]` и `EDX=old` без дополнительного явного stack argument; вызывает renderer vtable `+0x238`.
- Основная renderer vtable **0x00B18D38**, запись по **0x00B18F70** (`+0x238`) = **0x008353E0**. Эта функция сначала проверяет `old+4`; при signed count >1 вызывает `0x00839E30` (DWORD -1), иначе опирается на renderer frame-phase flag `+0x694` и либо откладывает pointer, либо запускает immediate release/cleanup.
- После возврата старого объекта, **0x0082BE99–0x0082BE9C** вызывает `0x00839E20`, тело `add DWORD [ecx],1; ret`, с `ECX=new+4`, только если new не NULL.
- **0x0082BEAA** записывает new (в том числе 0) в исходный slot. Возвраты renderer-release и increment-функции не проверяются.
- **Нет сравнения old и new на равенство** внутри данного блока. Из этого нельзя сделать вывод о дефекте без анализа владения ссылками и жизненного цикла.
- **Порядок доказан:** old release -> new increment -> store new. **Нет транзакционности** или возврата информации, была ли фактически уничтожена старая сущность. `AL=1` значит завершён путь замены, а не что GPU-ресурс обязательно освобождён.

## 7. Материал, caller/factory и потребитель deferred queue

**Прямые вызовы:** в полном objdump нет прямого `call 0x82be30`; исполняемый адрес найден как DWORD **0x0082BE30** по **0x00B17928** в material vtable. Поэтому обычная статическая таблица `call rel32` не показывает его реальных callers: это виртуальный метод через vtable slot `+0x60`. Описывать `0x0082A770` как *прямой caller* `0x0082BE30` нельзя: это **constructor**, устанавливающий соответствующий vptr.

Путь создания объекта (статический): renderer vtable **0x00B18D38 +0x200** по **0x00B18F38** содержит **0x0082DEE0**. Последняя на **0x0082DEE1–0x0082DEF4** выделяет 0x20 байт и вызывает `0x0082A770` с `EDX`-полученным исходным объектом как стековым аргументом. В конструкторе устанавливается material vtable `0x00B178C8`. Это подтверждает принадлежность virtual +0x60 к создаваемому renderer-ом семейству material.

**Статическая связь с очередь-путём** (не из runtime dispatch counts):
1. `0x0082BE8F` вызывает renderer slot +0x238 → `0x008353E0` (при standard renderer vptr).
2. `0x008353F3–0x0083540C` проверяет refcount old+4 и может сделать *только декремент* с ранним возвратом. Поэтому release не означает enqueue.
3. `0x0083540D–0x00835426` читает через renderer vtable +0x134 frame flag `renderer+0x694` и при nonzero AL выполняет `0x004CB900(ECX=renderer+0x1E80, EDX=&old)`, копируя DWORD pointer в слот контейнера.
4. `0x00835590` на **0x00835B35–0x00835B4B** работает **с тем же адресом `renderer+0x1E80`**, проверяет непустоту `0x0082F3C0` и извлекает через `0x00831380` в локальную переменную. Далее на **0x00835B53–0x00835B9C** при refcount==1 производит действия через виртуальные методы элемента, `0x00837DF0`, `0x008352F0` и финальный `[item.vtable+0x5C](1)`.
5. `0x00831380` возвращает `AL=1` при успешном pop, `AL=0` при пустом контейнере. Не всякий вызов `0x00835590` обязан выполнять pop, и не всякий вызов `0x0082BE30` обязан попадать в `0x008353E0`.

Это **одна и та же очередь по точному адресу и producer/consumer-коду**, без необходимости выводить её идентичность по номерам dispatch. Допускается называть её «отложенное освобождение/обработка material-owned pointer», но нельзя по одному статическому графу объявлять каждую замену фактическим удалением GPU-ресурса или draw.

## 8. Строгое отношение к runtime v728/v733/v734/v735

Заявленные в предшествующих пользовательских пробах факты: v735 имел 450 вызовов `0x008353E0` (445 из `0x0082BE30`), все возвраты `AL=1`; у этих 445 входов `renderer+0x694=1`; v733 — 460 (455 из `0x0082BE30`) и **нулевое число вызовов `0x004CB900` из `0x008353E0`** при наличии 32 вставок из других callers; v728 — лишь четыре sample вызова со значениями смежного getter 1/2; v734 — 1118 вызовов `0x00835590` без `0x00831380` из него, один `0x00831380` из `0x007EE360` вернул `AL=0`, выбранные Draw* импорты не наблюдались.

Ни эти счётчики, ни позиции dispatch **не доказывают**: (а) сколько именно material setter-вызовов выполнилось или успешно заменили указатель; (б) какие были old/new pointer и refcount во всех итерациях; (в) что в v733 после release достигался frame getter; (г) что отсутствие enqueue было вызвано конкретно `renderer+0x694`, а не ранним возвратом по `old+4`; (д) что `0x00835590` связан причинно с отсутствующими Draw*; (е) готовность, частоту или факт GPU отрисовки. Наблюдение v735 о флаге относится к **другому запуску**, не восполняет пер-вызовные факты v733.

Уточнение о наблюдаемом месте caller: 445/455 вызовов `0x008353E0`, зафиксированных с return address внутри `0x0082BE30`, согласуются с прямым исполнением **indirect CALL по 0x0082BE8F**, но их количество не позволяет установить распределение индексов, владельцев или типов ресурсов.

## 9. Confidence ledger

**Подтверждено retail EXE + objdump:**
- Хэш, границы `0x0082BE30–0x0082BEB3` с последующими `INT3` и отдельной `0x0082BEC0`.
- ABI ECX/material, EDX/unsigned index, stack/new pointer и `ret 4`; оба AL-исхода.
- `descriptor.vtable+0x34` возвращает exclusive верхнюю границу индексирования; неизвестно точное исходное имя этого количества.
- Ошибочная ветвь в штатной renderer vtable приводит к `[renderer+0x5E4]=4` через `0x0082E740`.
- Раскладка `+0x14` offsets и `+0x18` byte base, вычисление slot address.
- Инвалидация globals `0x00C26174/0x00C26178/0x00B8E418` по special material.
- Проверка old pointer, вызов renderer vtable +0x238, инкремент `new+4` и новая запись.
- Класс-семейство `CMaterial` по constructor vtable и соседним `CMaterial::...` D3DPERF strings; фабрика renderer `0x0082DEE0`.
- Отдельная consumer-ветвь по `renderer+0x1E80` в `0x00835590`, с `0x00831380`.

**Интерпретация с сильной поддержкой:** материал хранит типизированные поля в variable-stride blob; для некоторого типа `0x10` поле является refcounted указателем на объект renderer; setter +0x60 управляет сроком жизни ссылки; `0x00B8E418=3` означает обновление/инвалидацию состояния.

**Не установлено:** исходные имена material setter и метода descriptor+0x34, точное enum значение типа 0x10 и кода renderer=4, конкретные классы old/new, какие virtual +0x5C(1) реализации исполнялись, GPU draw reachability, причина отсутствия selected Draw* в запусках.

## 10. Ровно одна следующая retail-функция

**`0x0082A690`** — метод material state update, привязанный к UTF-16 маркеру **`CMaterial::SetShaderState`** (строка по **0x00B179C0**). Он использует тот же `[material+0x0C]` descriptor, его count virtual +0x34, виртуальные слоты +0x3C/+0x40, таблицу offsets +0x14 и blob +0x18; затем вызывает `0x0083D2E0` для применения состояния. Это конкретный следующий target для проверки **как данные material переходят к renderer state binding**, не подменяя исследование выводом о Draw* на основании только dispatch counts.

## 11. Полный retail objdump-блок 0x0082BE30–0x0082BEB3

~~~asm
0082be30: 55                   push ebp
0082be31: 8b ec                mov ebp,esp
0082be33: 56                   push esi
~~~
