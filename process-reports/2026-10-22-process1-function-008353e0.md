# Process 1 — retail-функция 0x008353E0: освобождение/отложенная обработка объекта renderer

**Дата:** 2026-10-22  
**PE:** Need for Speed Shift PC retail 1.02, x86 PE32, image base 0x00400000.  
**SHA-256:** `eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1` (проверено по `SHIFT.exe`).  
**Основание:** оригинальный бинарник и полный `SHIFT_objdump_full.txt`; runtime v728/v733/v734/v735 — строго данные, предоставленные пользователем, а не повторный запуск. Никаких изменений кода/PR.

## Итог

`0x008353E0` принимает `ECX=renderer`, `EDX=item`, стековых аргументов не читает; на всех штатных путях возвращает `AL=1`. Сначала проверяет счётчик `DWORD [item+0x04]`. **Если он >1 по знаковому сравнению** — декрементирует и возвращает 1, не читая `renderer+0x694`. Только при значении <=1 вызывает `[renderer.vtable+0x134]`, который для основной retail-vtable `0x00B18D38` разрешается в `0x0082DBB0` (`mov al,[ecx+0x694]; ret`). При ненулевом AL добавляет указатель `item` в контейнер по `renderer+0x1E80` через `0x004CB900`; при AL=0 выполняет ветвь непосредственной обработки (два условных снятия регистрации и завершающий виртуальный вызов `[item.vtable+0x5C](1)`).

**v733 zero child calls `0x008353E0→0x004CB900` не противоречат статическому графу:** эта ветвь достижима только после прохождения обеих проверок. Ни 460 входов в функцию, ни флаг на входе в других прогонах не устанавливают результаты проверки refcount и getter **в каждом вызове v733**. Процессорное число dispatch не является показателем GPU-отрисовки.

## 1. ABI, точный вход и возврат

- `0x008353E6 mov esi,edx`: `item = EDX`.
- `0x008353E9 mov ebx,ecx`: `renderer = ECX`.
- Локальный `[EBP-0x04]` по `0x008353F0` содержит копию указателя `item`; используется как `const void *`-подобный источник DWORD для контейнера. Это **не** дополнительный входной стековый аргумент.
- Входящих стековых аргументов нет; все три возврата — `ret` (`0x0083540C`, `0x00835433`, `0x0083547A`).
- Сохранены `EBX/ESI/EDI/EBP`. Возвращается `AL=1` (`0x00835406`, `0x0083542D`, `0x00835474`); старшие биты EAX не нормализуются. Нельзя трактовать DWORD EAX как достоверную единицу или AL как указатель на branch.
- Два регистровых аргумента совместимы с x86 MSVC `__fastcall`, но декларация компилятора/исходного C++ метода не доказана; реальный контракт — ECX renderer, EDX item и без `ret n`.
- Никаких прямых вызовов Draw* в самом блоке нет. Отсутствие Draw* во всей цепочке нельзя доказывать без дальнейшего разбора динамических виртуальных целей.

## 2. Первое условие: DWORD [item+4] и refcount

```asm
008353EB lea edi,[esi+0x4]
008353EE mov ecx,edi
008353F3 call 0x5e1d50
008353F8 cmp eax,0x1
008353FB jle 0x83540d
008353FD mov ecx,edi
008353FF call 0x839e30
```

Полный `0x005E1D50`: `0x005E1D50: mov eax,[ecx]`; `0x005E1D52: ret`. Он читает **DWORD [item+0x04]** без преобразований. `0x00839E30: add DWORD [ecx],-1; ret` уменьшает этот же DWORD. Ветка `jle` — **знаковая** (signed), а не `jbe`; сравнение выполняется до frame getter. При >1 функция делает decrement и прекращает работу с объектом.

Подтверждение значения как счётчика ссылок — родитель `0x0082BE30`: при сохранении нового ненулевого объекта `0x0082BE99–0x0082BE9C` вызывает `0x00839E20` с `ECX=item+4`, а `0x00839E20: add DWORD [ecx],1; ret`. Это доказанный инкремент/декремент; названия `refcount`, `Release` — сильная реконструкция, не символы бинарника. Из `v728` известны только четыре пробных входа с соседними getter-значениями 1 и 2; **они не определяют распределение** позднейших 445/455 вызовов.

## 3. Второе условие: slot +0x134 и +0x694

```asm
0083540D mov eax,[ebx]
0083540F mov edx,[eax+0x134]
00835415 mov ecx,ebx
00835417 call edx
00835419 test al,al
0083541B je 0x835434
0083541D lea ecx,[ebx+0x1e80]
00835423 lea edx,[ebp-0x4]
00835426 call 0x4cb900
```

У основной retail-vtable renderer `0x00B18D38` запись по `0x00B18E6C` (смещение +0x134) равна `0x0082DBB0`. Тело `0x0082DBB0`: `mov al,[ecx+0x694]; ret`. Это адресное разрешение **для объекта с этой vtable**; общий indirect CALL сам по себе допускает иную реализацию, если vptr заменён.

Ранее исследованная `0x0082F710` (`CRenderer::BeginFrame`) пишет BYTE `[renderer+0x694]=1` на `0x0082F762`, а `CRenderer::EndFrame` `0x00835D80` обнуляет его на `0x00835E86`. Это подтверждает интерпретацию как состояния начатого кадра, а **не** гарантирует вызов Draw*.

`0x004CB900` при `ECX=renderer+0x1E80`, `EDX=&[EBP-4]` копирует DWORD из локального источника (то есть указатель item) в слот (`0x004CB95E–0x004CB960`) и увеличивает DWORD счётчика контейнера (`0x004CB966–0x004CB979`). **Вызвать его в этом блоке можно только при signed refcount<=1 И nonzero virtual getter AL**. На иных ветвях сохранения в этот контейнер нет.

Независимое статическое доказательство, что это именно один и тот же контейнер producer/consumer: `0x00835590` на `0x00835B35` формирует `renderer+0x1E80`, проверяет его пустоту через `0x0082F3C0` (`0x00835B3D`), извлекает элемент через `0x00831380` (`0x00835B4B`), читает `[item+4]` (`0x00835B53–0x00835B5E`), затем при refcount==1 повторяет прямую обработку `[item.vtable+0x24]` (`0x00835B67`), `0x00837DF0` (`0x00835B6F`), `0x008352F0` с типом 5 (`0x00835B8E`) и `[item.vtable+0x5C](1)` (`0x00835B9C`). **Эта queue identity выведена из совпадающего точного адреса поля и операций push/pop, не из dispatch counts.** Название типа контейнера и семантика объекта остаются неустановленными.

## 4. Немедленная ветвь: виртуальный method +0x24

```asm
00835434 mov eax,[esi]
00835436 mov edx,[eax+0x24]
00835439 mov ecx,esi
0083543B call edx
0083543D test eax,eax
0083543F jbe 0x835448
00835441 mov ecx,esi
00835443 call 0x837df0
```

У `test eax,eax` `CF=0`, поэтому здесь `jbe` срабатывает **только при EAX==0**; любое ненулевое значение, включая бит 31, вызывает `0x00837DF0`. Не следует писать «только положительный EAX».

`0x00837DF0` итерирует глобальную структуру по адресу `0x00C26620` вызовами `0x007F1EB0` с `ECX=0x00C26620`, сравнивает найденное `DWORD [node]` с `item` на `0x00837E15`, а при совпадении вызывает `0x00837B00` с найденным ключом из `[EBP-0x0C]` (`0x00837E31–0x00837E34`). `0x00837B00` меняет статусы записи hash-like структуры (`0x00837B8E–0x00837B9A`); таким образом это **поиск и удаление записи по соответствующему item**. Точные class/type и смысл виртуального `+0x24` (например, признак регистрационной записи) не установлены. Возвращаемое значение `0x00837DF0` игнорируется.

## 5. Второе условное снятие регистрации: 0x008352F0

```asm
00835448 cmp BYTE [esi+0x15],0
0083544C jne 0x835454
0083544E cmp BYTE [esi+0x16],0
00835452 je 0x835467
00835454 cmp BYTE [esi+0x19],0
00835458 je 0x835467
0083545A push esi
0083545B mov edx,0x5
00835460 mov ecx,ebx
00835462 call 0x8352f0
```

Точное условие:
`(item[0x15] != 0 || item[0x16] != 0) && item[0x19] != 0`.

На входе `0x008352F0`: `ECX=renderer`, `EDX=5`, stack argument `[EBP+8]=item`; сам callee заканчивается `ret 4` (`0x00835357`). При ненулевом item он перебирает записи списка `renderer+0x1F20`: сравнение `[entry+0]==5`, `[entry+4]==item` на `0x00835327–0x0083532E`; при совпадении `0x00835346–0x0083534C` вызывает `0x006970F0`. Тот вызывает unlink helper `0x004E78B0→0x00516F90`, который меняет next/prev и уменьшает счётчик элементов `0x00516F93–0x00516FA5`. Это **поиск и удаление регистрации/записи типа 5**, а не команда draw. Названия битов +0x15/+0x16/+0x19 остаются неизвестными.

## 6. Финальный vcall

```asm
00835467 mov eax,[esi]
00835469 mov edx,[eax+0x5c]
0083546C push 1
0083546E mov ecx,esi
00835470 call edx
```

Выполняется всегда на непосредственном пути после условных снятий регистраций. Контракт: `this=item`, первый явный stack argument `1`, virtual slot offset `+0x5C`. Результат игнорируется; вслед за ним функция устанавливает `AL=1`. В `0x00835590` для отложенных объектов из `renderer+0x1E80` повторяется тот же slot/аргумент на `0x00835B93–0x00835B9C`. Это сильный признак операции release/destruction/cleanup; **конкретная реализация и гарантия deallocation не известны без item.vptr**. Называть это произвольным Draw* некорректно.

## 7. Связь со штатным caller 0x0082BE30

Из основной renderer vtable `0x00B18D38`: slot `+0x238` по адресу `0x00B18F70` содержит **`0x008353E0`**.

`0x0082BE30` осуществляет замену объекта в индексируемой таблице: после границ/возможной проверки состояния на `0x0082BE3E–0x0082BE71` читает старый slot pointer на `0x0082BE71–0x0082BE7D`. Если старый указатель не нулевой, берёт объект renderer из глобального `[0x00C26058]` и вызывает slot `+0x238` на `0x0082BE81–0x0082BE8F` с `EDX=старый указатель`. Затем, если новый указатель `[EBP+8]` ненулевой, на `0x0082BE99–0x0082BE9C` увеличивает `newItem+4` через `0x00839E20`, и на `0x0082BEA1–0x0082BEAA` записывает newItem в slot. Это обосновывает ABI `0x008353E0` как release старого объекта при смене ссылки, **но не гарантирует**, что конкретное runtime vptr в каждом событии было основным renderer vtable.

445/455 вызовов из `0x0082BE30` следует трактовать как вызовы этого обработчика в контексте **замены/обновления слота**, а не как draw submission.

**Логическое примирение v733:** при точной инструментальной регистрации нуля child calls условие `(signed [item+4]<=1) && (virtual AL!=0)` ни разу не выполнилось **при одновременном нормальном достижении** соответствующего CALL в выбранных событиях v733. Конкретное основание для каждого входа неизвестно: выход из-за счётчика >1 и/или нулевой getter после прохождения счётчика; возможны отличия в vptr. Флаг renderer=1 на входе 445 вызовов **v735** не отменяет ранний выход до чтения флага и не даёт статистики v733. Показания v734 о pop и Draw* — отдельные сведения, без доказанной причинной цепи.

## 9. Подтверждения, выводы, гипотезы

**Подтверждено retail-кодом:** ECX renderer, EDX item, три штатных AL=1 exit; signed counter+4 test/decrement; refcount increment при сохранении нового slot `0x82BE30`; main renderer vtable +0x134 → `0x82DBB0` → `+0x694`; адрес очереди `+0x1E80`; `0x4CB900` действительно пишет DWORD и наращивает размер; `0x835590` действительно извлекает из этой же очереди через `0x831380`; условие byte flags; поиск/удаление register entry type 5; завершающий virtual slot +0x5C(1).

**Сильная функциональная интерпретация:** функция обслуживает release/cleanup объекта; при начатом кадре откладывает его в отдельный контейнер для последующей обработки, иначе очищает регистрации и запускает финальный virtual cleanup.

**Не доказано:** исходные C++ символы item type, точные смысловые имена флагов и виртуальных методов, необратимое освобождение памяти при +0x5C(1), истинное распределение refcount среди 445/455 вызовов, прямой или косвенный выход на GPU draw, причинная зависимость отсутствующих `Draw*` от наблюдаемых dispatch counts.

## 10. Ровно один следующий target

**`0x0082BE30`** — главный runtime-родитель (445 входов v735 и 455 v733) через `renderer.vtable+0x238`, связывающий старый указатель, индексируемую таблицу и увеличение refcount нового указателя. Полный анализ его владельца/инициализации слотов/семантики замен лучше всего объяснит частые вызовы `0x008353E0` и поможет выбрать конкретную точку runtime-наблюдения счётчиков до того, как обсуждать какую-либо связь с draw.
