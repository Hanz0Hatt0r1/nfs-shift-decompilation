# Process 1 — retail function 0x0083B430: parameter-state dispatch

**Date:** 2026-10-22. **Binary:** Need for Speed Shift PC retail 1.02, PE32 x86, image base 0x00400000.  
**SHA-256 verified against original SHIFT.exe:** `eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1`.  
**Evidence:** original SHIFT.exe, complete SHIFT_objdump_full.txt, and user-provided complete function block. Retail virtual addresses below; no runtime code changes, no pull request.

## 1. Conclusion and scope

`0x0083B430` is a typed shader/effect **parameter setter/dispatcher**, not a draw function. It accepts a parameter index, uses an indirection array and an 0x50-byte record layout, checks a signed update-level guard, then dispatches on a type DWORD in `record+0x08`. The dispatch has **17 in-range type codes (1–17) but only seven distinct jump-table targets**. One target is explicitly a no-op returning success; unknown/out-of-range type codes also return success without applying state.

The underlying virtual call signatures and PE import `d3dx9_41.dll!D3DXCreateEffect`, together with neighboring +0xE8/+0xFC/+0x100/+0x10C uses, strongly identify `[controller+0x0C]` as an **ID3DXEffect-compatible interface**. Calls resemble SetValue, SetBool, SetFloat, SetVector and SetTexture. Exact runtime vptr and external implementation are not provided, so those API names are **ABI-derived identification**, not named exports at each call. Type 17 takes a separate renderer/device sampler-state route via `0x00846310`. No `DrawPrimitive`, `DrawIndexedPrimitive` or `Present` is emitted directly by this block.

## 2. ABI and arguments

| Location | Meaning, from machine instructions |
| --- | --- |
| `ECX` | `controller=this`; copied to ESI at 0x0083B43A |
| `EDX` | unsigned parameter index, copied to EBX at 0x0083B438 |
| entry stack `[ESP+4]` = `[EBP+8]` | pointer `value` to input bytes |
| entry stack `[ESP+8]` = `[EBP+0x0C]` | DWORD byte size `valueBytes` |
| `AL` | success/skip/failure indication (see path-specific caveats) |
| epilogues | `ret 8`, callee consumes both DWORD stack arguments |

ECX+EDX+two stack DWORDs is compatible with MSVC x86 `__fastcall` at the ABI level; original source C++ declaration is not established. Nonvolatile EBX/ESI/EDI/EBP are preserved when saved (EDI only after passing index bounds). Error and success paths can modify the upper 24 bits of EAX; only **AL** is the boolean contract.

The immediate caller adapter `0x0083D2E0` is `mov ecx,[ecx+0x5C]; jmp 0x0083B430` (**0x0083D2E3–0x0083D2E7**), preserving EDX and stack args. The one direct relative CALL to this adapter in the full objdump is **0x0082A70E** inside `0x0082A690` (`CMaterial::SetShaderState` according to the UTF-16 D3DPERF marker at `0x00B179C0`). `0x0082A70A` pushes computed parameter size, `0x0082A70B` pushes value address, `0x0082A70C` sets EDX=index; `0x0082A713–0x0082A715` tests AL and stops the iteration on zero. This confirms the normal material-driven entry route, **not** that all such parameters actually reach a GPU driver.

## 3. Bounds, indirect record selection, guard

- **0x0083B43C** `cmp ebx,[esi+0x48]`; **0x0083B43F** unsigned `jb` means `index < controller.count`. If index out of bounds, **0x0083B442** sets AL=0 and **0x0083B448** returns `ret 8`; no record accessed.
- **0x0083B44B–0x0083B45B**: `recordNo = DWORD [controller+0x50 + 4*index]`; `record = DWORD [controller+0x44] + 0x50*recordNo`. The arithmetic `lea ecx,[eax+eax*4]; shl ecx,4` multiplies by 80. `controller+0x50` is the *lookup array*, not record storage. `controller+0x44` is the record-array base. Record `+0x00` later supplies an opaque effect parameter handle, `+0x08` supplies type, `+0x0C` supplies a signed update guard value.
- **0x0083B45E–0x0083B468** calls `0x0083A4E0` with `EDX=[record+0x0C]`, `ECX=controller`. Its entire body is `xor eax,eax; cmp edx,[0x00B8E418]; setg al; ret` (**0x0083A4E0–0x0083A4EB**).
- Therefore if **signed** `record.field0C > signed global[0x00B8E418]`, control returns **AL=1 without applying the parameter** at **0x0083B46C–0x0083B474**. Equality does *not* skip. The executable initially stores DWORD 4 at `0x00B8E418`; `0x0083A4F0` sets it to 3 and `0x0083A500` sets it to 4. Its precise semantic label remains unproven; “update class/threshold” is a reasonable interpretation.
- The controller vtable is not used by this method; instead `controller+0x0C` is dereferenced to obtain a separate interface pointer, and that pointer's vtable is called in the branch handlers.

### Group 2 and group 3 conversion: 0x0064FD40

- **0x0083B50D** calls `0x0064FD40(ECX=P)` for type 8 when `N != 2`, obtains an x87 float, stores it as 32-bit float at `[EBP+8]` (overwriting the incoming pointer's stack slot), then pushes the resulting scalar **by value** to slot +0x78. The non-2 branch does not validate buffer length; it reads 16 bits at P even if N were too small.
- **0x0083B57B–0x0083B59B** calls the same helper with `ECX=P`, `P+2`, `P+4`, storing three float32 values to `[EBP-0x10/-0x0C/-0x08]`; `0x0083B59E–0x0083B5A9` sets the fourth value to **1.0f** at `[EBP-0x04]`. Slot +0x88 receives a pointer to this exact 16-byte vector. The non-6 branch similarly assumes at least six readable bytes despite the incoming size mismatch.
- The full `0x0064FD40` uses `movzx eax,word [ecx]`, bit extraction of sign/5-bit exponent/10-bit mantissa, exponent rebias and `fld` of constructed float bits. Special branches handle exact 0x0000 as +0.0 and 0x8000 via the bit pattern at **0x00AEE98C** as -0.0. This is **binary16-like → float32** expansion but it has no complete separate IEEE-754 handling for all subnormals/Infs/NaNs; do not label it a guaranteed fully standards-compliant half converter. It does not read/write the controller.
- The choice `N==2` or `N==6` sends raw compressed bytes via +0x50; `N!=2/6` converts input half words and dispatches float/vector. Why each downstream effect parameter expects one representation in a given material is not known without parameter descriptors. **Do not misread this as N==2 meaning float32.**

### Group 4 texture (type 16), fallback and object handle conversion

- **0x0083B5DA–0x0083B5E3** reads `textureObj = *(DWORD*)P`. If null, calls **0x00838F30**; this function creates/caches a fallback resource at global `0x00C26724`, its creation descriptor uses exact ASCII string **"Default Texture"** at **0x00B19810**. This is an actually observed resource-construction route, not an assumption from the type code.
- **0x0083B5E8–0x0083B5EF** calls **0x00838DF0** with ECX=textureObj. That helper reads `BYTE [textureObj+0x18]`. If nonzero (**0x00838DF0–0x00838E0D**), it uses renderer vtable+0x2E8 to set error/status **3** and returns zero. Otherwise it tests DWORD `[textureObj+0x08]`: only values 0/1/2 return the DWORD handle `[textureObj+0x38]` at **0x00838E20**; other kinds return 0. Thus the effect interface receives a **converted underlying texture handle or NULL**, not the engine texture-object pointer itself.
- **0x0083B5F4–0x0083B612** recomputes H and invokes interface slot +0xD0 with `(I,H,convertedTexture)`, mapping signed return to AL success. Precise 3D/cube/2D class identity by `textureObj+8` needs follow-up; vtable signature is consistent with `ID3DXEffect::SetTexture`.

### Group 5 special helper (type 17)

- **0x0083B626–0x0083B62D** dereferences `*(DWORD*)P` to obtain a pointer to a separate per-object state bundle, invokes **0x00846310(ECX=bundle, EDX=0)**, and directly returns its AL (no `setge` or effect `I` virtual method). There is no null check on the dereferenced bundle, so a null bundle could fail during execution of `0x00846310`.
- In `0x00846310–0x00846465`, ECX=bundle and EDX=sampler index; `0x0084631B–0x00846323` retrieves the active graphics device by `renderer=*[0x00C26058]` and `0x0082E110`; that getter returns `renderer+0x478` when device-ready byte `renderer+0x5E8` is set and otherwise stores renderer status 0xA.
- Based on `[bundle+0x0C]`, helper emits sequential virtual calls via device vtable **+0x114**, with first stack arguments device, EDX-supplied sampler index, sequential selector IDs 1..11, and corresponding DWORD values from `bundle+0x10..+0x38`; some later settings are converted from renderer floating values using x87. The +0x114 slot and argument layout are consistent with **IDirect3DDevice9::SetSamplerState**; this is state setup, not a Draw* call.
- **0x0084645D–0x00846465** returns `AL=1` without aggregating individual vcall HRESULTs. Therefore type 17's true return is not evidence that every sampler-setting call succeeded. Related UTF-16 marker `CShaderSpecialisation::SetInternalParameters` occurs at **0x00B19FC0** in neighboring specialization code `0x0083B130`, providing subsystem context, not a proven original enum name for type 17.

## 6. Interface and neighboring call evidence

The executable imports **D3DXCreateEffect / D3DXCreateEffectFromFileA** from `d3dx9_41.dll`. Other code in the same module uses the **same `[controller+0x0C]` interface**: e.g. `0x0083B670` selects techniques via virtual +0xE8, calls +0xFC with `(I,&passCount,3)`, and later calls +0x100 per pass, and +0x10C to end, all matching **ID3DXEffect SetTechnique, Begin, BeginPass, End** call shapes. Together with `+0x50/+0x58/+0x78/+0x88/+0xD0`, the typed parameter calls match the ID3DXEffect method family. This is strong API identification based on ABI/call geometry; no live vptr from runtime was supplied.

In the complete objdump, `0x0083D2E0` is the single direct tail-adapter to `0x0083B430`; its sole visible direct caller is `0x0082A70E`. Adjacent controller functions `0x0083B130` (marker `CShaderSpecialisation::SetInternalParameters`), `0x0083B2C0` (marker `CShaderSpecialisation::SetLightingParameters` at 0x00B1A020), and `0x0083B670` use other layouts and state-submission paths, corroborating that the `0x0083B430` body is in a shader/effect state manager, not a standalone renderer draw routine.

**Relevant distinctions:** `controller+0x48` is the parameter count for this indexed mapping; it is not `record+0x48`. `record+0x08` is the type discriminator, not the field controlling the signed guard. `record+0x0C` controls a pre-dispatch skip; the stored constant at `0x00B8E418` is mutable (initial 4, setters 3/4). Types 9/11/14/15 and unknown values return success **without touching the ID3DXEffect interface**, even if the record exists.

## 7. Confidence ledger

**Direct bytes/flow confirmed:** PE checksum; ABI/register use; `ret 8`; bounds `index < +0x48`; mapping `+0x50`, base `+0x44`, stride 0x50; guard with signed `setg`; seven jump targets and all 17 mapping bytes; exact stack pushes and vtable offsets; half-like conversion call sites and generated W=1; fallback "Default Texture" construction; `0x00838DF0` texture handle extraction/error status; `0x00846310` invocation and +0x114 virtual sampler path; AL treatment; material adapter `0x0083D2E0`.

**Strong API interpretation:** `[controller+0x0C]` is ID3DXEffect-compatible; +0x50 SetValue, +0x58 SetBool, +0x78 SetFloat, +0x88 SetVector, +0xD0 SetTexture, with HRESULT-like signed negative failure convention. `0x00846310` configures D3D9 sampler states via +0x114; type 17 is a special sampler-state bundle.

**Not demonstrated:** source-level enum names for all 17 values, full class identities or actual dynamic vptrs, meaning of the signed record level threshold, distinction among all raw SetValue-type semantic parameters, successful GPU execution just from nonnegative HRESULT, any Draw*/Present call, and any causal conclusion from host/guest dispatch counts.

## 8. Exactly one next retail function target

**0x0083B670.** It is the adjacent higher-level effect-technique/pass executor, entered via adapter `0x0083D2F0` after the shader-state preparation in observed material callers. Its `+0xE8/+0xFC/+0x100/+0x10C` virtual calls select a technique and start/process/end effect passes, and it invokes per-pass internal state routines.
