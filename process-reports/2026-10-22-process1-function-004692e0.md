# Process 1 — retail dispatcher 0x004692E0

Дата: 2026-10-22. Оригинальный NFS Shift PC retail 1.02, PE32 x86, ImageBase 0x00400000.
SHA-256 SHIFT.exe, проверен: eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1.
Источники: оригинальные SHIFT.exe и SHIFT_objdump_full.txt, данные v762 пользователя. Только анализ: без P-code/runtime/render изменений и PR.

## ABI, vtable, life cycle

Вход ECX=this; стековых аргументов нет; EDX входной не используется, неявные callee-saved ESI, EDI, EBX сохраняются. Нормальный return: EAX=1, обычный ret на 0x00469590 (в предоставленном пользовательском блоке последняя строка была подписана 0x00469591, однако оригинальный objdump однозначен). Функция совместима с __thiscall, но исходная декларация недоказана.

Подтверждено: конструктороподобные функции 0x0045EF50 (vptr store 0x0045EF78) и 0x00462E20 (vptr store 0x00462E33) пишут DWORD 0x00AB5644 по [this+0]. Проверка DWORD по PE: [0x00AB5644]=0x0066D450, [0x00AB5648]=0x004692E0, [0x00AB564C]=0x00466A80. Таким образом 0x004692E0 находится в vtable по адресу 0x00AB5648 — это **+4 относительно записываемого vptr 0x00AB5644**, либо **+8 относительно соседнего адреса 0x00AB5640**. Описание «slot +8 при vptr 0x00AB5644» арифметически неверно; для данного vptr вызов должен использовать [vptr+4]. На 0x0045F0D6 конструктор пишет ноль в [this+0x2B0]. Не наблюдены runtime vptr этого объекта или прямой rel32 call на 0x004692E0. Его возможная связь с внешним кодом — виртуальный вызов через vptr+4, но конкретный внешний caller без дополнительных данных не разрешен.

## Двухступенчатый gate и внешние side effects

BYTE [this+0x46C1] по 0x004692E3 управляет пропуском предварительного update:
- при нуле немедленный переход на switch 0x00469363;
- при ненуле: 0x00545D90 и вызов 0x0050CEB0 для returned pointer+0x108; singleton 0x00413EE0 с virtual +8/+0x14 (условно) и virtual +0x1C; 0x0040ED00(this); optional virtual +0x4C у [this+0xC4C]; 0x00518F10, если [this+0x2B0]==13; 0x004651F0(this); 0x00463890(this).
Затем независимо от gate выполняется state switch. Таким образом gate не отключает весь dispatcher: название типа ready/enable/active остается гипотезой.

После case также независимо от gate вызываются 0x0046F540 и 0x0046F340. На 0x0046945E флаг проверяется вновь: ноль обходит крупный post-update, неноль запускает цепочку 0x0080BFB0/0x0080BD80, 0x00647EF0 на нескольких subsystem objects, 0x00460730 с [this+0xCB0], запись [this+0x2A4], 0x00462D10, 0x0045C2E0, 0x0045F9A0, 0x00459410, и optional 0x00463680/0x00464230 при проверках +0xC50/+0x46C1 и 0x0050CEB0. На любом нормальном пути: 0x00633980→0x00633A50 перед EAX=1. Значения gate могут измениться между двумя проверками; это не loop-invariant, не «пропуск всей frame».
