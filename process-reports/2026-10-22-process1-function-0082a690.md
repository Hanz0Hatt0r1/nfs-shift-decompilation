# Process 1 — retail 0x0082A690 / CMaterial::SetShaderState

**Дата:** 2026-10-22  
**Бинарник:** Need for Speed Shift retail PC 1.02; PE32 x86, image base `0x00400000`.  
**SHA-256 (проверен по /mnt/data/SHIFT.exe):** `eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1`.  
**Источники:** оригинальный `SHIFT.exe` и полный `SHIFT_objdump_full.txt`; предоставленный пользователем блок совпадает по инструкциям. Все адреса ниже — retail virtual addresses. Только анализ; исходники не менялись, PR не создавался.

## Резюме

`0x0082A690` — retail-реализация операции **`CMaterial::SetShaderState`** (точная UTF-16 строка `CMaterial::SetShaderState` находится по `0x00B179C0` и передаётся по `0x0082A6AF–0x0082A6C5` в `D3DPERF_BeginEvent`). На уровне алгоритма метод принимает материал через `ECX` и идентификатор состояния через `EDX`, проверяет возможность пропустить повторное применение по глобальному кэшу, иначе записывает эту пару в кэш **до** выполнения работы, устанавливает текущий индекс в дескрипторе через `0x00839F20`, затем обходит все параметры дескриптора, поочерёдно применяя их через `0x0083D2E0 → 0x0083B430`. В штатном случае сообщает успех байтом `AL=1`; при первом неудачном применении сообщает `AL=0`.

Статически доказан путь установки **shader/material state**. Он не является прямым вызовом `Draw*` и не позволяет вывести достижимость GPU draw из счётчиков dispatch.

## 1. ABI, возвраты и собственные читаемые поля

- `0x0082A691 mov esi,ecx`: входной `ECX` — `material=this`.
- `0x0082A69B mov edi,edx`: входной `EDX` — 32-битное значение выбираемого состояния, сохранённое в `EDI`; оно передаётся в `0x00839F20` как `EDX` и сохраняется в глобальном `0x00C26178`. Называть его «shader pass index» возможно, но точное исходное имя/диапазон по одному этому блоку не определены.
- **Стековых аргументов нет**. `ESI/EDI` сохраняются, обе ветви завершаются обычным `ret` (`0x0082A6E1`, `0x0082A731`).
- Фактический контракт совместим с MSVC x86 двухрегистровым `__fastcall` (ECX объект, EDX индекс); классическая `__thiscall`-методика с *одним* стековым аргументом здесь не подходит. Исходную декларацию с уверенностью установить нельзя.
- Результат — **`AL`**, не нормализованный полный EAX: `xor al,al` на `0x0082A6DE`, `mov al,1` на `0x0082A72E`. Старшие 24 бита после предыдущих вызовов не гарантированно равны нулю.
- Непосредственные чтения: `[material+0x0C]` — указатель дескриптора; `BYTE [descriptor+0x60]` — разрешает/запрещает cache-fast-path; `[material+0x14]` — таблица DWORD байтовых смещений; `[material+0x18]` — начало blob значений. Непосредственные записи в material отсутствуют, но вызываемые функции меняют descriptor и внешнее состояние.

**Статическая привязка к material-семейству:** конструктор `0x0082A770` пишет в `[material]` vptr `0x00B178C8` на `0x0082A789`. Эта же область используется методами `0x0082BE30` (слот материала `+0x60`, запись таблицы `0x00B17928`). Близкий marker `0x00B17980` — `CMaterial::SetGlobalRenderState` (используется на `0x0082A660`), а marker `0x00B179C0` — `CMaterial::SetShaderState`; оба подтверждены прямым декодированием оригинальной .rdata. Привязка имени основана на instrumentation string и контексте, не на экспортированном символе функции.

## 2. Глобальный cache fast-path и когда он недоступен

~~~asm
0082a693 mov eax,[esi+0x0c]
0082a696 cmp BYTE PTR [eax+0x60],0
0082a69d jne 0x82a6af
0082a69f cmp DWORD PTR [0x00C26174],esi
0082a6a5 jne 0x82a6af
0082a6a7 cmp DWORD PTR [0x00C26178],edi
0082a6ad je 0x82a72d
~~~

**Точное условие немедленного AL=1 без D3DPERF Begin/End, записи кэша и применения параметров:**

`descriptor.byte60 == 0 && global[0x00C26174] == material && global[0x00C26178] == incoming_EDX`.

- Если `descriptor+0x60` **ненулевой**, сравнения с глобальными адресами **вообще не исполняются**, а работа повторяется. Семантическое название флага («force apply», «disable caching», «dirty») не установлено.
- Если material или index не равны кэшированным, также запускается полный путь.
- Полный путь **сначала** пишет `[0x00C26174]=material` (`0x0082A6B9`) и `[0x00C26178]=incoming_EDX` (`0x0082A6BF`), **потом** на `0x0082A6C5` вызывает D3DPERF_BeginEvent и начинает применение.
- Это кэш последней запрошенной **пары material/index**; он не измеряет завершение GPU draw, не хранит счётчик кадров и не доказывает, что привязка успешна.
- Функция `0x0082A630` — связанная инвалидация: `0x0082A632` и `0x0082A637` обнуляют оба globals, переходят через `0x0083A6F0` к `0x0083A4F0`, где `[0x00B8E418]` присваивается `3`. В предыдущем setter `0x0082BE30` инвалидация вызывается при изменении текущего кэшированного материала (`0x0082BE64–0x0082BE6C`). Не следует объявлять `0x00B8E418` кадром или HRESULT: его семантика иной подсистемы требует собственного анализа.

**Нюанс ошибки:** путь `AL=0` не отменяет записи `0x00C26174/0x00C26178`. При повторной идентичной паре, если `descriptor.byte60=0` и внешней инвалидации не произошло, возможно cache-hit `AL=1` даже после предыдущего отказа. Это **точное следствие локального кода** плюс условие о неизменности кэша, но не утверждение, что такая последовательность наблюдалась в runtime.

## 3. Строка-маркер и первая вызываемая функция

~~~asm
0082a6af push 0x00B179C0   ; UTF-16 CMaterial::SetShaderState
0082a6b4 push 0xFFFF0000
0082a6b9 mov [0x00C26174],esi
0082a6bf mov [0x00C26178],edi
0082a6c5 call 0x00923628    ; d3d9!D3DPERF_BeginEvent
0082a6ca mov ecx,[esi+0x0C]
0082a6cd mov edx,edi
0082a6cf call 0x00839F20
0082a6d4 test al,al
0082a6d6 jne 0x82a6e2
0082a6d8 call 0x00923622    ; d3d9!D3DPERF_EndEvent
0082a6de xor al,al
0082a6e1 ret
~~~

Полное тело `0x00839F20`:

~~~asm
00839f20 mov DWORD PTR [ecx+0x38],edx
00839f23 mov al,1
00839f25 ret
~~~

Это означает: `descriptor+0x38 = incoming index`, после чего `AL=1`. Поэтому `0x0082A6D4–0x0082A6D8` — **синтаксически существующий путь отказа**, но именно с этой фиксированной retail-реализацией `0x00839F20` он не достигается при нормальном выполнении. Не следует приписывать callee проверку допустимости индекса, GPU-operation или возможность вернуть false. Вызов на `0x0082A6CF` прямой, не virtual.

На всех путях, где выполнен `D3DPERF_BeginEvent`, код вызывает `D3DPERF_EndEvent`: при первом loop-failure через `0x0082A6D8` либо при loop-success/zero-count через `0x0082A728`. При cache-hit ни один event не вызывается.

## 4. Цикл descriptor+0x34/+0x40 и адрес параметра

После setter индекс **EDI=0** на `0x0082A6EA`. Для первого шага:

- `0x0082A6E2–0x0082A6EC`: `ECX=[material+0x0C]`; вызывается virtual `[descriptor.vptr+0x34]` без явных параметров; `EAX` — количество параметров. Его как upper bound также используют `0x0082BE30` на `0x0082BE41–0x0082BE45` и конструктор material `0x0082A890–0x0082A8C5`. Реальная implementation vtable дескриптора здесь не является statically-fixed: требуется descriptor.vptr конкретного runtime объекта.
- `0x0082A6EE test eax,eax; 0x0082A6F0 jbe 0x0082A728`. После `test` CF=0, поэтому переход эквивалентен count==0. Нуль → BeginEvent, запись кэша и установка descriptor+0x38 **всё же были**, но ни один параметр не применяется.
- `0x0082A6F2–0x0082A6FC`: virtual `[descriptor.vptr+0x40]` вызывается с `ECX=descriptor, EDX=i` и возвращает `EAX=size_i`. Смысл «размер в байтах» подтверждается использованием в конструкторе `0x0082A8B0–0x0082A8C5`, где эти значения суммируются перед выделением blob.
- `0x0082A6FE–0x0082A704`: `offset_i = DWORD [material.field14 + 4*i]`, `address_i = material.field18 + offset_i`.
- `0x0082A70A–0x0082A70E`: кладёт **size_i**, затем **address_i** на стек и вызывает `0x0083D2E0` с `ECX=descriptor, EDX=i`. Значит на входе callee `[ESP+4]=address_i`, `[ESP+8]=size_i`.
- `0x0082A713–0x0082A715`: `AL=0` немедленно прекращает дальнейший перебор и ведёт в EndEvent+return false; не происходит rollback ранее применённых параметров.
- `0x0082A717–0x0082A726`: снова вызывается descriptor.vtable+0x34 уже **после увеличения индекса** и сравнивается `i<count` через беззнаковое `jb`; при наличии элементов возврат на `0x0082A6F2`. Count перечитывается **на каждой итерации**, а не snapshot один раз до цикла. Нет локальной проверки корректности самих указателей `+0x14`, `+0x18` и размеров — они считаются валидными.
- `0x0082A728`: парное `D3DPERF_EndEvent`; `0x0082A72E` ставит AL=1.

Формула:

`parameterAddress(i) = (uint8_t*)[material+0x18] + *(uint32_t*)([material+0x14]+4*i)`.

Это **offset table + data blob**, а не массив `pointer[i]`. Предыдущий анализ `0x0082BE30` и конструктор `0x0082A770` независимо подтверждают схему раскладки и копирование descriptor-defined значений.

## 5. Полный доступный маршрут 0x0083D2E0 → 0x0083B430

`0x0083D2E0` не содержит самостоятельного применения GPU-состояния; это **tail-call adapter**:

~~~asm
0083d2e0 push ebp
0083d2e1 mov ebp,esp
0083d2e3 mov ecx,[ecx+0x5C]
0083d2e6 pop ebp
0083d2e7 jmp 0x0083B430
~~~

Таким образом, `descriptor+0x5C` — указатель на вспомогательный объект/контроллер параметров; `EDX=i` и оба стековых аргумента сохраняются, исполнение идёт прямо в `0x0083B430`. Эта функция завершает обычным `ret 8` и потому очищает оба DWORD.

Проверяемые внутренние действия `0x0083B430`:

1. **0x0083B43C–0x0083B448**: беззнаковая проверка `i < controller[0x48]`, иначе `AL=0; ret 8`.
2. **0x0083B44B–0x0083B45E**: `controller+0x50` содержит индексирующую таблицу DWORD, `controller+0x44` — базу записей с stride **0x50**; выбирается запись `recordIndex = DWORD [controller+0x50+4*i]`, `record = controller[0x44] + recordIndex*0x50`.
3. **0x0083B45E–0x0083B46A**: по `record+0x0C` вызывается `0x0083A4E0`; его тело `0x0083A4E0–0x0083A4EB` возвращает 1 при **signed `record.field0C > [0x00B8E418]`**. В таком случае `0x0083B46C–0x0083B474` сразу возвращает AL=1, то есть данный параметр **считается успешно обработанным без нижележащего state call**. Точное имя и роль этой метки/порога не установлены.
4. Иначе **0x0083B477–0x0083B48B** выбирается ветвь по DWORD `record+0x08` через jump table (`0x0083B63C`, `0x0083B658`). Разные ветви обрабатывают типы параметров и вызывают методы объекта `controller+0x0C` (его vtable slots в видимых участках: `+0x50`, `+0x58`, `+0x78`, `+0x88`); отдельные ветви преобразуют входные данные.
5. Многие ветви возвращают `AL = (signed EAX >= 0)`, проверяя HRESULT-подобный результат нижнего вызова через `test eax,eax; setge` (например, `0x0083B4A7–0x0083B4B6`, `0x0083B4CF–0x0083B4DE`). Таким образом `0x0083D2E0` **может** вернуть false из-за невалидного индекса/неуспешного применения параметра, в отличие от `0x00839F20`.
6. В `0x0082A690` ошибка останавливает цикл **на первом таком параметре**, без отката кэша, cursor или уже выполненных операций.

Это точный статический маршрут к интерфейсам **установки состояния/параметров**, но для утверждений об exact GPU API operation необходимо отдельно разрешить реальные vtable `controller+0x0C` и все ветви `0x0083B430`. По существующему материалу нельзя заявлять, что произошёл `DrawPrimitive/DrawIndexedPrimitive`.

## 7. Подтверждения, гипотезы, ограничения

**Подтверждено исходным retail-кодом:** hash и границы функции; ABI ECX/EDX и AL/ret; short-circuit descriptor+0x60; cache-hit только при равных material/index; преждевременное обновление двух globals; байтовая запись descriptor+0x38 через `0x00839F20`; D3DPERF Begin/End; descriptor virtual +0x34 как bound и +0x40 как размер; вычисление адреса по `+0x14/+0x18`; вызов адаптера `0x0083D2E0` с двумя DWORD аргументами; прекращение перебора на AL=0; повторный virtual count в цикле; шестёрка прямых callsites; имя UTF-16 marker.

**Сильно подтверждённая функциональная реконструкция:** method `CMaterial::SetShaderState` применяет набор типизированных descriptor-driven shader-state параметров; глобальные `0x00C26174/0x00C26178` кешируют последнюю выбранную material/index пару; `descriptor+0x60` отключает пропуск по этому кэшу.

**Не доказано:** исходная сигнатура C++ и имена полей, точный enum descriptor indices/types, неизменность count во время цикла, значения controller+0x0C virtual methods для всех конкретных объектов, гарантия восстановления кэша при ошибке внешним кодом, draw submission, D3D call count и какой-либо причинный вывод из runtime dispatch counts. Отсутствие доступа к runtime-объектам не позволяет полностью разрешить descriptor.vptr и controller.vptr.

## 8. Следующий **один** retail target

**0x0083B430.** Это непосредственный исполнитель всех per-parameter операций, достижимый из `0x0082A690` через tail-jump `0x0083D2E0`. Требуется полный разбор switch `record+0x08`, типизированных ветвей, выбора record по `controller+0x50/+0x44`, guard `0x0083A4E0` и виртуальных state-вызовов. Такой анализ различит ошибку применения параметров, оптимизационный skip и фактическую передачу состояния внешнему объекту — без домысла о draw.
