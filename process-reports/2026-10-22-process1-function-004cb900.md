# Process 1 — retail 0x004CB900: generic DWORD-add vs container 0x00BE2510 (stride 0x44)

**Дата:** 2026-10-22  
**Бинарник:** Need for Speed Shift PC retail 1.02, PE32, ImageBase `0x00400000`.  
**SHA-256 оригинального SHIFT.exe:** `eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1` (проверено через sha256sum).  
**Материалы:** полный `SHIFT_objdump_full.txt`, оригинальный исполняемый файл и данные v751, приведённые пользователем. Никаких изменений runtime-кода, данных контейнера или PR.

## 1. Ответ на главный вопрос

**`0x004CB900` структурно способна работать с инициализированным контейнером stride 0x44, но она НЕ подтверждена как реальный producer экземпляра `ECX=0x00BE2510`.** Дизассемблирование не содержит жёсткой проверки stride==4: slot allocator `0x004CB6D0` адресует слоты с фактическим `DWORD [container]`. Однако сам `0x004CB900` записывает **только DWORD [input]** в первые четыре байта слота; он не конструирует/копирует остальные 0x40 байтов сложной записи. Более того, в одном из grow-путей `0x004CB6D0` переносит только DWORD на каждый старый элемент, хотя использует реальный stride при расчёте адресов. Это серьёзное свидетельство специализации add под DWORD-подобные элементы, но **не математический запрет вызова с более широким stride**: вызывающий код мог бы инициализировать остальное отдельно при соблюдении ограничений роста.

Для конкретного v751 provenance наблюдал только один writer нулевого значения: `0x0062FDE0` записал `0x00BE2534=0` (sequence 2378600, dispatch 462758), и по всем 585 дальнейшим samples до dispatch 811880 writer не изменился. При условии полноты targeted write trace для этого адреса **ни одно нормально дошедшее до 0x004CB979 исполнение `0x004CB900` с `ECX=0x00BE2510` после init не имело места** в охваченном интервале, поскольку такое исполнение обязательно писало бы именно DWORD `0x00BE2534`. Это не доказывает, что функция никогда не вызывается с этим receiver в иных состояниях/прогонах или что не существовало прерванного вызова до `0x004CB979`.

## 2. Точный ABI и контракт

- `ECX` = адрес **самого контейнера**, копируется в ESI на `0x004CB906`; не адрес owner, не pointer-to-pointer.
- `EDX` = адрес **источника DWORD**, копируется в EBX на `0x004CB90D`. По `0x004CB95E mov edx,[ebx]` считываются *четыре байта* из `[input]`; затем `0x004CB960 mov [edi],edx`. Не копируется содержимое массива, строка или весь `stride`.
- Стековых входных параметров нет, конец `0x004CB984: ret` (не `ret n`). Совместимо с MSVC x86 `__fastcall` (ECX/EDX), но исходное C++ объявление по одному ABI недоказуемо.
- В `EAX` на возврате находится **адрес выделенного слота** (`0x004CB97C mov eax,edi`), либо 0 если allocator вернул NULL; это **pointer**, а не AL-булево.
- Сохраняются EBP/EBX/ESI/EDI, а EAX/ECX/EDX могут меняться.
- Для штатного выполнения требуются валидный ECX, источник DWORD при ненулевом slot, рабочие указатели блоков; отсутствует проверка валидности `EDX` перед `mov [EDX]`.

## 3. Полная ветвизация `0x004CB900`

1. **0x004CB908–0x004CB927**: тестируется `BYTE [container+0x2C] & 8`. При 0 вызывается `0x0062FF90` с `ECX=container, EDX=0` и 7 DWORD: **(0,4,4,0x1F,1,0,0)**. Это *lazy initializer* с 4-byte stride. Его внутренний вызов `0x0062FDE0` — тот же семейный инициализатор, но не следует смешивать это с независимо наблюдавшейся цепочкой `0x004E8BC0 → 0x0062FFD0`, которая инициализировала 0x44.
2. **0x004CB92C–0x004CB941**: если `[container+0x18]==0`, `0x0062F2D0` выделяет первый блок с `capacity=[container+4]`; полученный pointer записывается в `+0x18` и `+0x1C`. Важный момент: отсутствие блока не запрещает add — блок создаётся лениво. `0x0062F2D0` на `0x0062F2DB–0x0062F2E5` рассчитывает байтовый размер как **[container+0x00] × capacity**, а не жёстко 4.
3. **0x004CB944–0x004CB946**: вызывается `0x004CB6D0` с ECX=container; получает указатель на **новый слот**, обновляя внутренние block-count метаданные.
4. **0x004CB94B–0x004CB955**: два нуля на стек и `ECX=EDX=0` перед `0x00457CC0`; последнее — `ret 8` (адрес 0x00457CC0), no-op по наблюдаемой семантике, ничего не копирует/не конструирует.
5. **0x004CB95A–0x004CB964**: если slot != 0, выполняется DWORD `*slot = *input`; если 0, пропускает чтение/запись и ставит EDI=0.
6. **0x004CB966–0x004CB979**: всегда на нормально достигнутом пути читает DWORD `[container+0x24]`. Если старое значение 0, записывает `[container+0x30] = DWORD[[container+0x18]+4]`, то есть cached base pointer первого блока. Затем **без дополнительного контроля успешности slot** увеличивает count на 1 и сохраняет в `[container+0x24]`.
7. **0x004CB97C–0x004CB984**: возвращает pointer слота в EAX, восстанавливает регистры. Ни один normal return до 0x004CB979 не предусмотрен, кроме исключения/fault внутри helper.

**Оговорка:** отсутствие проверки slot !=0 перед увеличением count — реальный локальный факт, но не доказательство, что allocation failure встречался или не обрабатывался низкоуровневой политикой ошибок.

## 4. Slot allocator `0x004CB6D0`: совместимость stride 0x44 не решается одним размером

**Основной случай, когда у последнего блока есть capacity:**
- `0x004CB6DA–0x004CB6E3`: читает lastBlock=[container+0x1C], сравнивает `[lastBlock+0x14]` с `[lastBlock+0x10]`.
- **0x004CB7A8–0x004CB7B6**: `address = [lastBlock+4] + [container+0]*[lastBlock+0x14]`; затем `[lastBlock+0x14]++`. На **0x004CB7B9–0x004CB7C0** `[container+0x28]` синхронизируется с count первого блока. Эта арифметика **позволяет шаг 0x44**.
- `[container+0x24]` внутри allocator напрямую не инкрементируется: это делает caller `0x004CB900`.

**Если блок заполнен:**
- **0x004CB6E9–0x004CB6FF**: если `[container+8]!=0`, создаётся/пристёгивается следующий блок через `0x0062F2D0`, last pointer обновляется. Здесь не видно копирования старого содержимого.
- **0x004CB704–0x004CB70B**: если `[container+8]==0`, вызывается `0x0062FF00` для нового блока/grow, затем проверяется флаг `[container+0x2C]&1`.
- **0x004CB716–0x004CB736** (`flag&1 !=0`): перенос старых элементов bulk-copy через `0x00900DEA` с размером `[oldBlock+0x10] * [container+0]`, т. е. **полным byte stride**.
- **0x004CB73B–0x004CB789** (`flag&1 ==0`): перенос каждого сохранённого элемента в цикле, адреса вычисляются с фактическим `[container+0]`, но сам перенос по **0x004CB774–0x004CB776** использует **`mov edx,[ebx]; mov [edi],edx`**, то есть копирует лишь первые 4 байта, а не `[container+0]` байт. В частности, это не корректная полная копия 68-байтового объекта с живыми данными после DWORD0.
- **0x004CB78A–0x004CB7A5**: обновляются block metadata, cached head-data pointer и освобождается старый блок.

В v751 у этого экземпляра были параметры init: `[EBP+8]=0`, `[EBP+0xC]=0x44`, `[EBP+0x10]=4`, `[EBP+0x14]=0x1F`, `[EBP+0x18]=0`, `[EBP+0x1C]=0`; callback возвратил AL=1. Предшествующая `0x0062FDE0` устанавливает `WORD [container+0x2C] |= 8` (**0x0062FEE3**) и обнуляет count **0x0062FEE8**. При сохранении флагов стандартный lazy-init 4-byte путь `0x004CB900` поэтому **был бы пропущен** и allocator использовал бы уже существующее `stride=0x44`. Сам init с flags=0x1F **не выставляет автоматически** helper-флаги +0x2C&1/+0x2C&2 через ветви `flags&0x20/0x40`; однако другие mutators/внешние источники могут их позднее изменить.

**Вывод:** `0x004CB900` не имеет явной проверки `stride==4`; потенциально она могла бы создать слот 0x44 и записать его начальный DWORD. Но это **не полноценный конструктор 0x44-элемента**; для контейнера, где в `0x0050CF40` деструкторы вызываются по `element+0,+4,+0xC` (см. `0x0050CF79–0x0050CF8B`), такой DWORD-only copy не воспроизводит семантику корректной вставки целого элемента. Особенно опасен путь роста с per-record DWORD copy. Следовательно, *semantic mismatch* сильно поддержан; абсолютный запрет вызова или отсутствие частичной вставки не установлены.

## 5. Direct callers: полный статический rel32-аудит

Скан по **всему** `SHIFT_objdump_full.txt` с привязкой к x86 `call rel32` и target **0x004CB900** выявил **401 различных адресов CALL**. Это все обнаруженные **прямые** callsite в данном выводе objdump; вызовы через function pointer / непрямой dispatch и статистика фактических исполнений ими не охватываются.

- В диапазоне **0x0050C000–0x0050D0FF** (содержит `0x0050CEB0`, `0x0050CF10` и соседние методы контейнера) **нет прямых `call 0x004CB900`**. В более широкой области 0x0050xxxx есть CALL по **0x0050B092, 0x0050B188, 0x0050B2FF, 0x0050DD59, 0x0050E3CC**.
- **0x0050B092:** `ECX=&[EBP-0x6C]`, `EDX=&[EBP-8]` — временный/локальный контейнер. **0x0050DD59:** `ECX=[EBP-0x1C]+0x34`, `EDX=&[EBP-0x20]`, принадлежность к outer `0x00BE2500` не доказана. **0x004E36D5:** `ECX=[EBP+8]+0x3C`, `EDX=&[EBP-0x14]`. **0x004CBA5C:** `ECX=EDI+0x18CC`, `EDX=&[EBP-4]`. **0x00835426:** `ECX=renderer+0x1E80`, `EDX=&localItem` и очевидно используется для DWORD pointer queue, отличный от заданного экземпляра.
- Указатели `0x00BE2510` и `0x00BE2500` не встречаются как точные x86-иммедиаты в полном objdump (случайная последовательность байтов внутри инструкции `0x008BBE3D` не является символической ссылкой). Это **не доказательство отсутствия runtime-алиасов**, если адрес формируется из heap/глобального pointer/индексирования.
- `0x004E8BC0` из установленной цепочки init не вызывает `0x004CB900`; `0x0050CF10` — переход/thunk к `0x004E8BC0`, а не producer. Статического непосредственного ребра от указанных функций/участков к `0x004CB900` нет. По одному адресу callsite из иных функций нельзя доказать `ECX=0x00BE2510`, когда ECX вычисляется динамически.
- Наличие прямых callsite в 0x00Dxxxxx отражает код .secu в retail PE; наличие rel32 **не доказывает runtime reachability** при конкретном запуске.

## 6. v751: что именно следует и не следует из provenance

Runtime v751 (дано пользователем, не запускалось повторно): 120 host frames, `validation_errors=0`. Наблюдалась цепочка `0x004E8BC0 → 0x0062FFD0 → 0x0062FDE0` с `ECX=0x00BE2510`, AL(inner)=1, stride `0x44` и params выше. Последний видимый writer `0x0062FDE0` сохранил DWORD `0x00BE2534=0` (sequence **2378600**, dispatch **462758**, size=4), сохраняясь во всех **585** следующих gate samples до dispatch **811880**.

**Подтверждено в заданном окне:** значение count 0 на samples и отсутствие другого writer в сохранённой targeted provenance. **Сильный условный runtime-вывод:** в этом окне после init не было достигшего конца и записавшего count исполнения любого add, включая `0x004CB900`, **именно с этим receiver**. Это не доказывает отсутствие всех producer-кандидатов в retail-коде, причину того, что они не были вызваны, отсутствие незавершённого вызова, состояние других объектов или связь с Draw*. Отсутствие selected Draw imports в v751 — отдельный факт, не причинное объяснение через count.

## 7. Confidence ledger

**Точно по retail байтам/objdump:** ABI; два указателя receiver/source; условие lazy-init; аргументы default инициализации; адреса первого блока; обращение к allocator `0x004CB6D0`; DWORD-only копирование; безусловный count++ на main path; first-item cached data pointer; EAX=slotPointer; реальные stride-based вычисления адресов, блоковые ветви копирования и 401 rel32 CALL; отсутствие прямого CALL в исследуемом `0x0050C000–0x0050D0FF`.

**По пользовательскому runtime v751:** конкретный receiver init и параметры, last writer и counts. Не нужно додумывать число вызовов `0x004CB900` — трассировка была targeted write provenance, не census всех его входов.

**Ограничения:** реальные динамические ECX всех 401 site не восстановлены; callsite без literal может через alias попасть в нужный объект; не доказаны исходные C++ type names; не известно, какие именно поля 0x44 записи обязаны конструироваться при вставке; возможные other-producer/indirect calls не исключены; прямых причинных выводов о GPU draw нет.

## 8. Ровно один следующий retail target

**`0x0062F6F0`** — generic slot acquisition для блочного контейнера, встречающийся у ряда специализированных callers; необходимо проверить, какие вызывающие пути получают слот для 68-байтовой записи, где и когда после этого инкрементируется `container+0x24` и как конструируются три нетривиальных вложенных поля. Это полезнее, чем автоматически назначать `0x004CB900` producer только по схожему layout. Runtime watchpoint на `0x00BE2534` остаётся независимым способом проверить реальные записи, но **единственный следующий retail function target** в этом отчёте — `0x0062F6F0`.
