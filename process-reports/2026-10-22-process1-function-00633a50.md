# Process 1 — retail function 0x00633A50 (NFS Shift PC 1.02)

Date: 2026-10-22  
Scope: static retail binary and full objdump analysis only. No source changes, no PR.  
Executable: SHIFT.exe, PE32 x86, image base 0x00400000.  
SHA-256 (verified locally): eca479aa2d8dbb88bc55709d91ae5c7159ae1b00fc9555d6701000c26de8aee1

## Executive finding

0x00633A50 is a parameterless wrapper over the global manager returned by 0x0065BF80, which returns singleton address 0x00BFB4A0 (after conditional one-time initialization). It does two distinct things:

1. Process the list at manager+0x44 through 0x0065B8B0, returning the latter's count of selected item invocations.
2. Walk the list at manager+0x24. For each non-null item selected by the predicate manager[0x64] != 0 OR item[0x148] != 0, construct a temporary description via 0x0065B430 and immediately destroy that temporary string.

Its own instructions do not issue Direct3D Draw* calls. The second pass formats diagnostic information about update frequencies; it does not by itself prove a persistent log write or render submission. The call into the first pass ultimately reaches 0x00647EF0, which can have further effects and must not be treated as a no-op. An end snapshot PC=0x00633A50 in v723 is not a causal proof of the missing guest Draw* calls.

The manager constructor includes the literal string "_BManagerSys Critical" (0x00AEFD0C); a related manager controller path uses "BManager Controller" (0x00AEFCE8). These support the update/manager interpretation; they do not conclusively name the original C++ class of every involved object.

## Calling convention, arguments, and return value

- At 0x00633A50 no incoming stack arguments are accessed. The epilogue is plain RET at 0x00633AE8, not RET n.
- Incoming ECX and EDX are not read. Although all four observed callers set ECX from 0x00633980 immediately before the call, 0x00633A50 overrides ECX before each use; do **not** reconstruct that ECX as this.
- The appropriate logical signature is a zero-argument routine returning a 32-bit integer. Calling it __cdecl is ABI-compatible, but no-argument code alone cannot uniquely distinguish all x86 calling convention declarations.
- EAX on return is restored from [EBP-0x8] at 0x00633ADF, containing the value returned by 0x0065B8B0 at 0x00633A6B. This is **not** the result of the predicate at 0x00633A8E, is **not** an AL boolean, and is not necessarily a count of successful updates: 0x0065B8B0 increments its counter after invoking 0x00647EF0 without examining that invocation's return value.
- EBX, ESI, EDI and EBP are saved/restored. Locals: [EBP-0xC] four-byte iterator scratch, [EBP-0x8] saved result, [EBP-0x4] temporary string handle.

0x00633980, which is called by the four parents and then assigned to ECX, is a distinct one-time initializer returning 0x00BF9B29. It is not the manager actually traversed by 0x00633A50. Inside the target the manager comes instead from two calls to 0x0065BF80 (0x00633A59, 0x00633A60).

**List layout — distinguish observed fields from names:** Let L = manager+0x24 for the second pass, or L = manager+0x44 for the first pass.

- 0x0067DB80 at 0x0067DB80 checks DWORD [L+0x00]. If zero it writes zero to the iterator output. Otherwise 0x0067DB8E–0x0067DB94 obtains a pointer at [L+0x10] and reads DWORD [that+0x04] as the starting node.
- 0x004F5EB0 at 0x004F5EB0 checks DWORD [L+0x00]; when nonzero 0x004F5EBE–0x004F5EC1 copies [L+0x14] into the iterator output. In the zero case its branch at 0x004F5EB7 goes to 0x0042EFF7, which writes zero to the iterator output and jumps back to 0x004F5EBD/RET.
- 0x00633AC7 reads node+0x04 to advance; 0x00633A95 reads node+0x0C to obtain the item. The list is **pointer-linked**, with a terminal/end marker. Whether its node layout is precisely std::list, a custom list, or a sentinel-based implementation cannot be decided from these observations alone.
- The code only tests L+0x00 for zero; do not silently equate it with a conventional STL count field without checking list mutators.
- 0x0065BD70 initializes manager+0x24 and manager+0x44 as separate list-like structures (0x0065BD75–0x0065BDBE), and zeroes manager+0x64 at 0x0065BDC3.

**Item data and gate:**

- 0x00633A95: item = DWORD [node+0x0C].
- 0x00633A9C: BYTE [manager+0x64] checked first; when nonzero item+0x148 is *not read on that path*.
- 0x00633AA2: BYTE [item+0x148] tested only when manager+0x64 is zero.
- No assignment to either flag is performed by 0x00633A50.
- A non-null item passes the gate exactly when (manager[0x64] != 0) || (item[0x148] != 0). The exact source-level names and whether these flags indicate debug verbosity, eligibility, profiling or something else are unverified.

**First-pass callee 0x0065B8B0:**

- Its stack argument [EBP+0x08] is the list pointer manager+0x44; it walks nodes using the same 0x0067DB80 and 0x004F5EB0 helpers.
- At 0x0065B8E0 it reads item = [node+0x0C]. At 0x0065B8E3, 0x0065B8E9, 0x0065B8EF it requires bytes item+0x34, +0x35 and +0x29 all nonzero.
- On passing all three tests it writes BYTE [item+0x240] = 1 at 0x0065B8F5, calls 0x00647EF0 at 0x0065B8FC, and increments EBX at 0x0065B901. At 0x0065B91D it returns EBX as EAX.
- Importantly, 0x00647EF0 itself starts by clearing BYTE [item+0x240] at 0x00647EFD and testing item+0x29 at 0x00647EF9. The temporary write at +0x240 must not be characterized as a durable mode change without tracing the callee.
- Thus the result is the number of qualifying attempted invocations of 0x00647EF0 in that pass, *not* necessarily the number of successful updates, objects rendered, or frames.

**Description callee 0x0065B430:**

- 0x00633AB3–0x00633ABA passes two explicit stack arguments: [EBP+0x08]=item; [EBP+0x0C]=pointer to caller's temporary string. The callee ends in RET 8 at 0x0065B53F. Incoming ECX is overwritten without being read in that callee.
- The item has a name/string pointer at +0x24, checked at 0x0065B443 and used in formatting at 0x0065B469.
- 0x0065B487 reads item+0x34, 0x0065B4A0 reads float item+0x144, 0x0065B4A6 reads byte item+0xDC, 0x0065B4B9 reads double item+0xE0 (on one branch), and 0x0065B4F4 reads double item+0xC0.

## v723 context, frontend/render and the missing Draw*

The only runtime statement supplied is that a bounded 360-host-frame recompiled-P-code run (v723) had its main-thread end snapshot at 0x00633A50 and had no guest Draw* and no capture. That proves the sampled PC and absence of observed guest Draw* within that test window; it **does not** establish how many instructions the target executed, whether it returned, that it is hung, that it is the last blocker, or that it caused the draw absence.

Direct static evidence argues against labeling 0x00633A50 a draw routine: it iterates BManager lists, conditionally invokes an update method via 0x0065B8B0 -> 0x00647EF0, and constructs discarded diagnostic strings, without direct draw-interface dispatches in the shown block. There can be an *indirect* relation to rendering (e.g. scheduled objects whose update work is required before rendering), but that is **unproven**. The upstream callers are consistent with periodic application and state-machine pumping and do not isolate a frontend or GPU stage. A single snapshot is compatible with ordinary execution through a common per-frame routine.

To establish causality later, one would need repeated PC/entry-exit samples or a bounded trace proving lack of forward progress, and a control-flow trace showing whether 0x00647EF0 (or subsequent parent paths) reaches graphics submission. Those are proposals, not observations from v723.

## Confidence ledger

**Confirmed by executable + objdump:** SHA-256; exact function instructions; no incoming arguments read; singleton manager address; two list addresses; iterator and node offsets; short-circuit predicate; direct callee arguments; temporary string lifetime; return counter; four direct callsites; quoted format strings; flag writes/reads in 0x0065B8B0 and opening of 0x00647EF0.

**Strong inference:** the BManager subsystem schedules/updates objects and can format diagnostic per-item frequency/status descriptions. Node+0x04 is the next link and node+0x0C the payload pointer.

**Unproven:** exact original C++ symbols and type declarations; meaning of +0x64 and +0x148 beyond their gate behavior; identity of the four parent systems as purely frontend/render; that diagnostic string production writes a log; that v723 stopped or stalled inside this function; causal link to absent Draw*; definition of “successful update” inside 0x00647EF0.

## Single next retail target

**0x00647EF0**. This is the executed work routine reached at 0x0065B8FC for qualifying items, also called directly at 0x0054A632 on one branch of 0x0054A520. It clears item+0x240 (0x00647EFD), tests item+0x29 (0x00647EF9), and proceeds into extensive branching and calls. An end-to-end analysis of that one function is the most useful next discriminator between an update/scheduling dependency and an actual graphics-submission path. Do not label it Draw* until its own callees support that interpretation.
