## Evidence interpretation

The runtime reached the host frame loop and executed clear/present work, but these observations do not demonstrate a guest D3D9 draw, frontend readiness, or gameplay. Dispatch totals are telemetry only. In particular, v747 reported fewer dispatches than v743 (1,722,972 versus 1,736,004); both ran 360 frames with 4,728 unique functions and zero validation errors, so this counter difference alone is not a regression signal.

Static inspection of retail `0x0082F3C0` shows it returns whether `[ECX+0x24] == 0`. `0x0050CEB0` checks that result and, on the observed path, returns zero when the state/callback conditions are absent. Process 1's full analysis report `process-reports/2026-10-22-process1-function-0062fde0.md` identifies `0x0062FDE0` as a block-container initializer: it initializes `[this+0x24]` and `[this+0x28]` to zero after its allocation/setup call; neighboring removal logic decrements them. In v751 the exact receiver was `0x00BE2510`, and every later sampled gate retained the initializer as the last writer. This supports an empty container throughout the measured window, not a readiness flag. Do not force the field.

The input probe establishes delivery through the Win32 message queue and the game's WndProc default path for Up. It does not establish that all keyboard/mouse input is unused. The selected DirectInput/XInput/cursor imports were simply not observed in this bounded window.

The v753–v755 trace establishes the runtime path `0x00A69160 -> 0x0040BA50 -> 0x0054BE00 -> 0x00835D80` for this bounded startup loop. `0x0040BA50`'s byte check at `[this+0x140D]` was zero for receiver `0x00BBF960`; no guest P-code writer to address `0x00BBFD6D` was recorded. This is a concrete inactive branch to analyze, not yet a proven frontend or rendering gate. The loop still performed frame-stage calls, while no selected D3D9 Draw import was entered.

v756 establishes that the renderer's primary vtable slot `+0x138` reaches `0x0082F780` with a nonzero device pointer and in-frame byte set. This active setup path and its two children still produced no D3D9 Draw import entry. It narrows the frontier to later content/submission work without proving which guest function should submit a draw.

The v757 call trace extends the active path one level outward. It confirms that the persistent `0x0040BA50` frame function repeatedly calls `0x00405DA0`, `0x00647EF0`, and the `0x00409FF0`-provided object before reaching the same renderer frame-stage path. The zero returns from `0x00405DA0` and `0x00647EF0` are observations only; their contracts and effect on frontend progress are not established. This run did not produce a Draw/DrawUP call or capture. Its 3,930 unique-function count is run telemetry and is not compared with other runs that may use different supplemental P-code manifests.

The v758 caller trace resolved `0x00405DA0`'s first indirect method to `0x00633370`; the call uses ECX=`0x00BBFF80`, the address passed by the caller as the `this+0x620` slot. The method returned EAX=0 in all 587 observed calls. That supports an empty/no-result path for this method in the measured window, but the meaning of the result and the source of queue records remain to be established from the retail body and producer paths.

The v759/v760 comparison exposed a configuration-dependent managed DXT3 boundary. With the capture-directory variable absent, v759 stopped at the managed-texture validation before reaching the frame loop. With it set, the same retail PE, runtime binary, game-data tree, P-code manifest, and frame bound completed 360 validated host frames. In that temporary P2 integration, `D3d9PacketCaptureAdapter::install()` advertised DXT3 support, while `shift_runtime.cpp` installed that adapter only when `SHIFT_D3D9_PACKET_CAPTURE_DIR` was nonempty; the P1 managed-texture path rejected compressed formats that the active adapter did not advertise. Process 2 then added the capture-independent managed-DXT3 capability in PR #2145. Its focused CTest passed in a local integration build based on P1 commit `89a01999` plus P2 commit `de073773`. The v763 no-capture replay crossed the exact earlier texture-description stop and completed the same 360-frame host loop. This verifies the limited capability fix against the retail startup path. It does not establish DXT3 Vulkan sampling, frontend readiness, or a guest draw. The v760 and v763 traces both recorded no Draw/DrawUP imports; v763 also reported `guest_draw_translation=false`.

v761 follows the main-menu-event producer candidate `0x004052B0` recommended by Process 1's `0x00405DA0` analysis. Its non-truncated trace selected that function, its queue-enqueue helper `0x004049D0`, allocator `0x0045B530`, and all four Draw/DrawUP imports; it recorded no selected events in 360 frames. This is bounded evidence that this candidate path did not run in v761, not evidence that the function is unreachable or that its absence causes the missing menu.

v762 added the static transition chain from Process 1 report commit 4564f0d5. Retail 0x004692E0 dispatches through the table at 0x00469594 using [this+0x2B0]; state 17 selects the case at 0x0046944B, which calls 0x0045C000, whose tail jump reaches 0x004052B0. The bounded v762 call trace selected 0x004692E0 and 0x0045C000 as well as the producer, allocator, enqueue helper, and Draw imports; it recorded no events. The v763 no-capture trace selected the same targets and imports and again recorded no events. Neither bounded trace establishes that the state was zero or that the function is unreachable: the dispatcher may not have been entered. Process 1 is analyzing the dispatcher's lifecycle and state writers.

v764 traced the active caller path from the v763 main-thread snapshot. In the saved prefix, 0x0054BB20 called 0x00633980 at return address 0x0054BB45 with ECX=0x00BBF960; it returned EAX=0x00BF9B29. The next call was 0x00633A50 at return address 0x0054BB4C with ECX=0x00BF9B29; all 1,010 saved calls completed with EAX=0. These are observed call/return facts, not a semantic name for the object or a causal link to the main-menu dispatcher. The trace hit its 8,192-event limit, so counts are only for the retained prefix. No selected dispatcher or Draw/DrawUP event was saved. This path was a candidate before Process 1's dispatcher report; that report later identified the exact state store at 0x0045B236 and the conditional state-17 callsite at 0x00463325, leaving 0x00633A50 as a separate candidate.

Process 1's dispatcher report, revised at `work/process-reports` commit `76291115`, corrects the vtable arithmetic: with vptr base 0x00AB5644, the pointer at [vptr+4] is 0x004692E0. The dispatcher reads [this+0x2B0]. The report identifies 0x0045B1E0 as the shared state setter and 0x0045B236 as its store, then finds a state-17 writer at 0x00463325 inside 0x00463120. That write is conditional on AL==0 from 0x00623640, and the dispatcher would only take the state-17 case on a later entry. v768 selected that caller and the setter/dispatcher/producer targets but recorded no entries. Process 1 is now resolving the external virtual-call site and object flow for the vptr+4 dispatch.

v765 selected the 0x0045B1E0 setter, 0x004692E0 dispatcher, constructor candidates, producer path and four Draw imports. Its non-truncated trace recorded one call to 0x0045EF50 from 0x00D36210, with ECX=0x27DFC520 and return address 0x00D362DE; no setter, dispatcher, producer, or Draw import entry appeared. v766 repeated that target set and enabled write provenance for address 0x27DFC7D0, the reported object's [this+0x2B0]. At constructor entry, that word sampled as zero; the attached last-writer record refers to an earlier 128 MiB guest-memory zero-initialization range at 0x20000000, not a sample after the constructor's own store. v767 reproduced the same constructor path and recorded all six bounded calls from 0x00D36210, ending at the constructor. v768 then selected the state-16 writer/caller and dispatcher/producer chain; its non-truncated event list remained empty. Together these runs show that the constructed object and its state-17 path were not observed entering the selected update chain in these windows; they do not prove permanent unreachability or explain why the frontend has not advanced.

### v751 receiver and write provenance

The wrapper entry was dispatch 462,712 (`caller=0x004E8BC0`, `return=0x004E8BE3`, `ECX=0x00BE2510`). Its nested initializer entry was dispatch 462,713 (`caller=0x0062FFD0`, `return=0x0062FFF6`, `ECX=0x00BE2510`); both returned `EAX=1`. The six initializer stack arguments were `0, 0x44, 4, 0x1f, 0, 0`, establishing a 0x44-byte element stride for this initialized container. At completion dispatch 462,758, the provenance record identified `0x0062FDE0` writing a four-byte zero to `0x00BE2534`. The v751 call trace and UI-gate trace were enabled and not truncated. Across 585 subsequent gate samples, that same write remained the last writer, so no later P-code write to the exact address occurred in this run.

Process 2's report `process-reports/2026-10-22-process2-v743-no-draw-frontier.md` confirms that the checked P1-to-P2 wiring has one typed `DrawIndexedPrimitive` handler and no tested route that bypasses its import/adapter callback. The present trace therefore places the observed frontier before that P2 draw ingress. An unknown hook or untraced guest route is not ruled out.
