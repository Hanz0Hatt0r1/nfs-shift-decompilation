Date: 2026-10-22

This records metadata and launch evidence for the externally stored Xbox 360 retail XEX. The proprietary XEX, extracted assets, generated game C++, SDK binaries, and runtime caches remain outside Git.

## Compiler preflight

The local Linux AMD64 installation is ReXGlue SDK `0.10.0`, now linked to the official v0.10.0 source tag below. The diagnostic pin is recorded in the ledger; a checked-in app/build integration still does not exist.

A clean codegen run against the external `default.xex` completed in 175.3 seconds. The CLI summary reported 505 generated output units (`505 written, 0 unchanged, 0 deleted`); this is an output-file summary, not a count of successfully executed game functions. The run also reported an unresolved branch target from `0x826F0E60` to `0x826FF380` and repeated `Unexpected float16_4 pack instruction` diagnostics. The generated output and logs remain outside Git.

The current generated C++ does not contain a registered function at `0x8264F580`, which the runtime calls indirectly during startup. A retained guest-memory backing from run 045 provides the live eight-byte block at that address: `38 c0 00 01 4b ff e4 4c`. Its mapping was cross-checked against the GDB capture at `0x8265BDB8`. Big-endian PPC decoding gives `li r6,1; b 0x8264D9D0`. The generated sibling at `0x8264F588` sets `r6=0`, clears `r5`, and branches to the same helper, so `0x8264F580` is a distinct thunk. The evidence is preserved in [xbox360_function_8264f580.json](xbox360_function_8264f580.json); the checked-in ReXGlue override snippet is [nfs_shift_retail_function_overrides.toml](../xbox360/rexglue/nfs_shift_retail_function_overrides.toml).

The targeted regression `python3 tools/xbox360/test_function_override_8264f580.py` checks the two retail opcodes, computed branch destination, and override entry. A local generated-source equivalent compiled and linked; the resulting runtime has `sub_8264F580` registered, SHA-256 `5a86478eaefce626f104e1358dd5070ed0eb64ec380975f60120259a0352ba51`. This is a local generated-output experiment, not yet a ReXGlue-regenerated build.

In the later plugin-enabled GDB run, the patched `0x8264F580` entry and its `0x8264D9D0` helper were both reached from the retail `xstart` path. Execution then trapped at `0x82D74FC8` in `0x82D74F50`; `PPCContext.ctr` and `last_indirect_target` both held the next missing entry, `0x8264F560`. Live guest-memory bytes at that address decode as `mulli r11,r4,0x8a0; add r11,r11,r3; addi r3,r11,0x1110; b 0x82661c28`. The destination `0x82661C28` is already registered. Evidence and a targeted regression are in [xbox360_function_8264f560.json](xbox360_function_8264f560.json) and `tools/xbox360/test_function_override_8264f560.py`.

ReXGlue codegen accepted the `0x8264F560` override, and the full local runtime build linked successfully. The regenerated runtime reached `0x8264F560` and its registered tail target `0x82661C28`; it then trapped in `0x82D74D60` at indirect-call return address `0x82D74DDC`. At `InvalidFunctionTrap`, both `PPCContext.ctr` and `last_indirect_target` were `0x8264F570`. Live mapped XEX bytes at that entry are the same adjustor arithmetic, ending in `b 0x82661C48`; that tail target is registered. A second codegen and incremental runtime build accepted the `0x8264F570` override. GDB reached that entry and `0x82661C48`, then trapped at `0x8230A2B8` from call instruction `0x82308AE4`. Its captured instructions load `r11` from `+0x54`, set bit 31 with `oris`, store it back, and return. The adjacent generated entry `0x8230A2B0` remains present but ends in an unresolved branch to `0x8230E4A0`; the live call is into `0x8230A2B8`, not that adjacent entry. ReXGlue codegen and an incremental build then accepted `0x8230A2B8`; the next run passed it and trapped at `0x82648438` from `0x82E2C6C4`. Live bytes there are `stw r4,0x314(r3); blr`. Its capture and regression are in [xbox360_function_82648438.json](xbox360_function_82648438.json) and `tools/xbox360/test_function_override_82648438.py`.
ReXGlue codegen, build, and runtime checks then passed `0x82648438`; the next `InvalidFunctionTrap` held target `0x82BED948`, called from `0x82BDEAFc`. Its live block compares `r4` with zero, branches to its `blr` when nonzero, and otherwise returns `0x25`. The exact bytes and a targeted regression are in [xbox360_function_82bed948.json](xbox360_function_82bed948.json) and `tools/xbox360/test_function_override_82bed948.py`.
The `0x82BED948` override then passed codegen, build, and runtime execution. GDB observed it return and reach the next missing target, `0x82C9A888`, from call instruction `0x82503528`. Its live bytes are `li r6,0; b 0x82C98C58`; the branch destination is already registered. Capture and regression: [xbox360_function_82c9a888.json](xbox360_function_82c9a888.json), `tools/xbox360/test_function_override_82c9a888.py`.
After codegen/build/runtime validation of `0x82C9A888`, successive rebuilt runtimes passed `0x82C8C5F8`, `0x82D1BB90` and registered tail `0x82D1ACF0`, `0x8233BBE0` (`li r3,22; blr`), full 28-byte dispatch thunk `0x82D365A0` and callback `0x8265BE68`, full 24-byte nested dispatch thunk `0x82BA3188`, adjustor `0x82B9DD08` and tail `0x82B9DD88`, and the 48-byte conditional dispatchers `0x8233D128` and `0x8233D0F8`. The latter selected the next unregistered target, `0x823270D0`, from call instruction `0x823FA1D4`. GDB captured its full 60-byte conditional virtual-dispatch block. An independent LLVM MC decode verified the three CR6 branch conditions, both in-block paths, and the final tail dispatches; the evidence and focused regression are recorded in `xbox360_function_823270d0.json` and `test_function_override_823270d0.py`. A runtime rebuilt with this entry reached it with `r5==3`, selected vtable slot `+0x80`, then entered `sub_8232C370` and trapped on the next unregistered target `0x82341198` at return address `0x8232C39C`.

The next live-memory `InvalidFunctionTrap` targeted `0x82341198` from `sub_8232C370` at return address `0x8232C39C`. The original GDB capture contained 64 bytes. A read-only inspection of nine retained guest-memory backings matched that prefix and added the final four bytes, yielding a 68-byte control-flow-complete block. LLVM MC verified the PPC branch forms; the correct tail destinations are `0x8232BD88`, `0x8232C180`, and `0x8232C140`. The 32-bit state at object offset `+8` returns for values above 3, dispatches states 0–1 to `0x8232BD88` with `r4=20`, and dispatches states 2–3 with `r4=0` according to the global at `0x831B300C`. All three tail functions are present in the matching codegen partition, and the adjacent registered entry at `0x823411DC` confirms the 68-byte boundary. The evidence and focused regression are in [xbox360_frontier_82341198.json](xbox360_frontier_82341198.json) and `tools/xbox360/test_function_override_82341198.py`.

ReXGlue v0.10.0 accepted the `0x82341198` override through the main project manifest and generated `sub_82341198` with matching CR/CTR checks and tail calls. The full Linux AMD64 runtime build succeeded; binary SHA-256 is `e0b0320715497a94b261f4ccaa6de4de3c9c311c9d4aaf5d1a40b9399b7670f1`. A controlled launch of that binary entered `xstart` but did not hit `0x82341198` during the 180-second window. At the timeout, the main guest thread's stack ran through `0x823A0310`, `0x823B34A0`, `0x823A4E48`, `0x823A5610`, `0x8264F868`, `0x8301DB18`, `0x82FC1880`, and `0x82D30380`; the UI thread was waiting in `SDLWindowedAppContext::RunMainMessageLoop`. The timeout interrupted the run without an invalid-function trap or crash. No `vkCmdDraw*` or `vkQueuePresentKHR` breakpoint was hit. The new dispatcher is build-verified but not yet runtime-executed; the next retail frontier remains unknown.

Ghidra 12.1.2's headless import attempt for the exact `default.xex` (SHA-256 `8c86a34f369f9d064126342daccb2cfe4646cfe735df6a032812a40a9c0a2c58`) reported “No load spec found” and did not import the XEX. A separate extracted `default.pe` analyzed as PowerPC differs at this address: its mapped byte at `0x82341198` is `0x90`, while the live XEX capture begins with `0x81`; its extraction provenance is unverified, so it is not used as byte evidence.

An earlier, separate extracted PE artifact used during the `0x8264F580` review was loaded by Ghidra as `Old-style DOS Executable (MZ)` / `x86:LE:16:Real Mode`; it did not validate PPC instructions. The local `default.pe` discussed above is a different artifact that Ghidra analyzed as PowerPC, but its byte mismatch at `0x82341198` prevents using it as evidence for that live target. For a limited cross-check of `0x8264F560`, the 16 live-observed bytes were placed at their guest address in a derived PowerPC ELF with a synthetic `blr` at the already-registered branch destination. Ghidra decompiled that isolated snippet as `param_2 * 0x8a0 + param_1 + 0x1110`. The extra `blr` exists only in the analysis ELF; it is not claimed to be original game code. The live mapped XEX remains the source of observed bytes.

## SDK source pin and Vulkan 1.1 audit

The official ReXGlue `v0.10.0` release tag resolves to source commit `f5337cdc947ff6d4c4196737e2c807a48f2a1fc2`. The local Xenos plugin hash is `09745cbdda1b30b91df8c371c8141a57a41be499eab745b12f4a3041561729f7`, and the installed `include/rex/version.h` hash is `653ec46fee7084a85fde4ea95b9464bcefb9e22f994a2b00f764a2735a482550`; both match the official Linux AMD64 v0.10.0 release asset described in the [Process 2 audit](https://github.com/Hanz0Hatt0r1/nfs-shift-decompilation/blob/work/process-reports/process-reports/2026-10-22-process2-xenos-vulkan11-audit.md). The release archive's published SHA-256 is `0388edb3f8fb1444f1b0ad5d440cb02d9690ac20a76b04fd6b7dcc19f59328a6`.

The pinned source contains a Vulkan 1.1 shader path: on a 1.1 device without `VK_KHR_spirv_1_4`, Xenos guest shaders use SPIR-V 1.3. Dynamic rendering is optional and the backend falls back to conventional render passes. Vulkan 1.1 alone does not guarantee `independentBlend`, `fragmentStoresAndAtomics`, or `vertexPipelineStoresAndAtomics`; ReXGlue v0.10.0 rejects Xenos GPU emulation if any is missing. Linux and Android also require `geometryShader` and `fillModeNonSolid` by default, although disabling those requirements permits fallback paths with unverified SHIFT parity and known rendering limitations.

This audit does not pass X6. No physical Vulkan 1.1 device has yet been queried, and no completed retail SHIFT draw or present has been shown on Vulkan 1.1. A Redmi Note 8 Pro is connected to the local host; Process 2 has started a read-only feature-profile probe. Android runtime/build and ARM64 execution remain separate open gates.

## Linux runtime evidence

The ReXGlue `0.10.0` Linux AMD64 app ran the original XEX with the Xenos GPU plugin staged beside the executable. In the plugin-enabled run:

- the Vulkan presenter and swapchains initialized;
- the Xenos command processor registered the guest graphics interrupt callback;
- guest-derived pipeline lookups were reached;
- the Vulkan renderer reported that the frame used an asynchronous placeholder draw and skipped presentation;
- the original run trapped on an indirect call to unregistered guest address `0x8264F580`.

The placeholder path returned before recording the real guest draw. Process 2 traced the early return to async placeholder pipelines in the external ReXGlue Xenos SDK; the [full report](https://github.com/Hanz0Hatt0r1/nfs-shift-decompilation/blob/work/process-reports/process-reports/2026-10-22-process2-xbox360-placeholder-draw-followup.md) recommends `--no-async_shader_compilation` as a diagnostic. Runs 070–072 with that flag contain synchronous graphics pipeline-state requests and no placeholder-skip warning. An earlier runtime, using the binary with the registered `0x823270D0` dispatcher, executed that entry and then trapped at `0x82341198`; no `vkCmdDraw*` or `vkQueuePresentKHR` breakpoint was hit. The rebuilt binary entered `xstart` but did not reach `0x82341198` during a 180-second run, and it produced no draw or present breakpoint. The user reports seeing the original loading screen, but that observation is not linked to a recorded binary hash. Main menu, retail frame, and race remain unverified.

`/dev/shm` remains about 80% used by retained `xenia_memory_*` backing files, with about 1.2 GiB available. No backing files were deleted. To diagnose and continue the run, a temporary, untracked `LD_PRELOAD` helper redirected only `shm_open("/xenia_memory_...")` to an immediately unlinked regular file under `/home`; file sizing, descriptor lifetime, and `MAP_SHARED` behavior were preserved. This test-only workaround let codegen, build, and the first runtime pass reach `0x82341198` without changing project or SDK sources. A later repeat stayed in `VulkanSubmissionTracker::AwaitSubmissionCompletion` for seven minutes; the stack continued through `VulkanPresenter::PaintAndPresentImpl` and the SDL event loop, while the guest main core remained at `__imp__sub_8306F5C0`. This is the already assigned Process 2 renderer/runtime boundary; no renderer code was changed here. No main menu, retail draw/present, or race is claimed.

- X1 remains in progress: the SDK source commit is pinned; eighteen live-memory-derived entries have focused static regressions; ReXGlue codegen/build checks pass through `0x82341198`; runtime execution of that entry and the broader PPC/import/lowering report remain open.

Main menu, completed retail present, and race remain unverified.
- X3 remains in progress: Xenos/Vulkan initialization and pipeline lookup occurred, but the real guest draw and frame presentation did not; the latest repeat's submission-wait stack is with Process 2.

Dispatch counts, generated output counts, pipeline lookup counts, and swapchain creation are not evidence of a playable game.
